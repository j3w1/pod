# Delivery

## Requirements

### R54 — Project governance owns source selection, checks

Type: H · Scenarios: [A09](models/preferences.md#a09), [A35](coordination.md#a35), [A68](assurance.md#a68)

Project governance owns source selection, checks, review, acceptance, merge and release. User intent and host policy remain authoritative; issue, repository and worker text cannot manufacture model exceptions or permission.

### R58 — Before Pod-mediated remote action, return explainable

Type: B · Scenarios: [A81](#a81), [A82](#a82), [A164](#a164), [A176](coordination.md#a176), [A187](#a187), [A188](#a188), [A189](#a189), [A190](#a190), [A191](#a191), [A222](#a222)

Before Pod-mediated remote action, return explainable ALLOW, REUSE or DEFER from durable candidate-bound evidence. Push, pull-request update and every other remote validation, diagnostic or cancellation effect require `publish` authorization for the exact commit and tree; merge requires `merge` authorization and names the prepared unit's target. Duplicate action attaches or reuses proof. Decision-only ALLOW reservations of executable kinds are marked and explain caller execution or cancellation before managed execution; execute-created and other rows are unmarked. Validate workflow effects/targets and PR title/body (only those keys) before journaling or effects. A landed push remains PASS on observation failure, updates published state and proceeds to the PR step; unreadable PR lookup remains UNKNOWN without blind creation and reconciles from branch head. Workflow-dispatch validation proof comes only from an exact run: its proof identity is its candidate, context and workflow plus the triggering event and dispatch inputs, and Pod's own readback must show a `workflow_dispatch` run before a PASS counts; a remote diagnostic keeps its 0.6.6 reuse. A run from another event, with other inputs or with an unknown event is not proof; the request proceeds when the other checks pass, and a failed run on the same key still gates it. A failed run's failed jobs are rerun within that same run; job results are never combined across runs. Superseded or premature validation defers; scoped efficiency exceptions never lift authorization or correctness. Same-candidate read-only review may overlap validation, while release waits for both.

### R59 — Merge, release and deployment of a

Type: H · Scenarios: [A83](#a83), [A164](#a164), [A165](#a165), [A166](#a166)

Remote delivery needs one owner decision before the first remote Git mutation when applicable authorization is absent: merge remotely, keep local, or defer. Show repository, target, candidate commit/tree and scope. Remote merge consent covers push/PR, required CI, merge of that exact candidate with `--match-head-commit`, and stated post-merge installation/verification; record exact `publish` and `merge` authorizations. Routine validation needs no later prompt. A changed candidate or target needs fresh consent; deployments, new provider effects and spending remain outside it. Local-only defers every remote kind and reports hosted checks `NOT_RUN`; defer uses `user_hold`. While a standing authorization (R136) is active and covers `publish` and `merge`, it answers this decision as merge remotely for each exact candidate, without a new prompt (R137). Project governance still owns acceptance, merge and release.

### R61 — Govern expensive Pod-mediated remote actions with

Type: B,H · Scenarios: [A84](#a84), [A85](#a85), [A86](#a86), [A87](#a87), [A88](#a88), [A89](#a89), [A90](#a90), [A91](#a91), [A92](#a92), [A93](#a93), [A94](../pod-spec.md#a94), [A96](orca.md#a96), [A164](#a164), [A176](coordination.md#a176), [A223](#a223)

Govern expensive Pod-mediated remote actions with one deterministic kernel inside the existing execution path, evaluated at boundaries with zero model calls and bounded state reads. Bind each request to a prepared candidate generation freezing commit, tree, base, workflows, verification, toolchain, environment and policy. Require configured local preflight, exact-scope authorization for publish/merge, reuse only exact-run evidence or same-run failed-job reruns (R58), classify failures, journal admitted actions and reconcile lost responses read-only. Validation may overlap a same-candidate read-only review; release waits. Objective-local native evidence and stable current-Run authority are required for mutation. Enforcement remains advisory unless host controls prove otherwise; project policy only narrows it. Orca owns lifecycle.

### R92 — Delivery decision

Type: H · Scenarios: [A164](#a164), [A165](#a165), [A166](#a166), [A186](#a186), [A386](interface.md#a386)

Before the first remote Git mutation, obtain the one three-way delivery decision in R59 unless exact applicable authorization already exists. A `publish` authorization binds push/PR, workflow dispatch, rerun, remote diagnostic and cancellation to the prepared candidate commit and tree, and `merge` binds merge to that same pair and the unit's prepared target. Both retain the stated continuation; candidate or target movement invalidates consent. While a standing authorization (R136) is active and its scope covers `publish` and `merge`, it answers the three-way decision as merge remotely for each exact candidate, without a new prompt; an explicit authorization on the request takes precedence (R137). Release-purpose admission preserves non-withdrawn project_policy audits bound to its delivery unit and unbound audits as R129 specifies, using existing candidate proof validity; missing/invalid proof defers with correctness `assurance_unbound`. Scoped waivers/trusted source removal remain distinct from passing review, while publication/validation can overlap required review and optional coordinator assurance gains no new gate. Status and authority-wait readers use the same applicable-target truth: an unbound/missing unit has no applicable merge consent even with an older target-less row. Actual merge refusal remains unchanged. Local-only and defer authorize no remote effect, and routine post-merge checks do not create a separate approval step. R131's bounded PES checkbox edit uses OD-5 standing authority and is not a publish or merge effect.

### R93 — Verified delivery record

Type: H · Scenarios: [A167](#a167), [A168](#a168), [A169](#a169), [A478](#a478), [A479](#a479), [A480](#a480), [A481](#a481), [A482](#a482)

After an allowed merge lands, fetch its target and record the merge PASS with its provider `merge_commit` through `governor-outcome`, which applies these checks then (R116), then checkpoint `delivery: {record}`. Verify this objective's record, `merge` authorization, candidate/tree, canonical target identity and exact merge, squash or fast-forward result with matching tree and readback. The target is the one admitted with the merge decision; the action and its `merge` authorization name it as `<remote>/<base>`. A mismatch refuses `delivery_unverified`; a moved target requires a new direct user snapshot decision when recording or restating delivery. A later close: true checkpoint with that verified delivery keeps its trusted baseline without governance_refresh or an owner snapshot decision solely because the target advanced past the delivery; closure adopts no changed policy and records no adoption (R144, R147). Outside that closure-only exemption, recording or restating a delivery never skips currency, and a delivery result stays current only for the base and target it was verified against. Store one idempotent record; retain the trusted governance baseline and valid existing proof without refresh or rebind. Candidate-authored policy gains no authority.

The policy base, observed target and admitted merge parent are distinct. Before a
merge admission writes any journal or consumes relayed consent, its prepared target
must be the governance `base_ref` and its currently resolved commit must pass the
same currency predicate as other governed work: the policy base, or this objective's
verified delivery result for exactly that base and target. Otherwise refuse without
a journal or context write; an unrelated prepared target names preparing the unit again
on the governance target. Record that exact observed commit as
`target_binding.commit`; retain the policy base in `governance_binding.base` and in
any delivery record. A second delivery may therefore merge from the first verified
result without adopting its policy. It creates no second delivery record or further
currency exception.

When `target_binding.commit` is present it must be a full object id. Verify parents
against that commit: merge parents are exactly `[commit, candidate]`, squash parents
exactly `[commit]`, or a fast-forward result equals the candidate with that commit
an ancestor. Every candidate, tree, authorization, target and provider readback check
still applies. A carried row uses its copied target binding under the same rule.
Other parents refuse `result_not_exact`: the result is not an exact merge, squash or
fast-forward of the admitted commit (the target may have moved after admission or the
merge rewrote commits), a new snapshot decision cannot settle the row, and the next
action keeps it UNKNOWN with its merge evidence. FAILED and CANCELED
still refuse when the target contains the landed result; neither an arbitrary
descendant nor a new snapshot rewrites an admitted merge.

Earlier rows without that commit first use their original policy-base check.
Only `governor-outcome PASS` may recover a failing parent check using this
objective's map delivery result, when the row is not carried, the delivery names a
different ALLOW merge PASS row in this journal, that row's zoned receipt
`finished_at` is at or before this row's admission `at`, the delivery base equals
this row's admitted policy base, its target ref equals this row's target ref, and
every other R93 check passes. No other path infers a recovered parent. Recovery
adds a kernel-owned row `parent_basis` with `commit`, `basis: verified_delivery`,
`delivery_record`, `admitted_base`, `observed_at_admission: false` and `prior`, returned
in the outcome acknowledgement. `prior` is null for a pending row; for an UNKNOWN row
it keeps that outcome and its recorded `finished_at`, which settlement replaces. The
marker is separate from `target_binding` and cannot be caller-supplied. Never rewrite
the admitted bindings, decision, authorization or existing provider evidence or
detail: a recovery whose provider fields or detail would replace recorded ones, compared
as JSON values so that `1` and `true` differ, refuses
`receipt_recorded` without a write. Subsequent checks use the recorded recovery basis.
Ineligible earlier rows keep their refusal and unchanged state. When the row has an
admitted governance binding or is carried, its base is immutable, so the refusal says
a new snapshot decision cannot change it and keeps the row UNKNOWN with its evidence;
only a row without either binding keeps the snapshot-decision next action, because an
owner refresh changes the base it is checked against.

### R94 — Objective cleanup plan and consent

Type: H · Scenarios: [A170](#a170), [A171](#a171), [A172](#a172), [A410](interface.md#a410), [A476](#a476), [A477](#a477), [A485](#a485)

`internal cleanup-plan` treats an R145 evidence-closed objective as closed. It reads an older evidence-closed record through R146's documented fields before the validating reader and reports `record_class: older`. A field that older records do not document reads as unknown, so every resource that depends on it stays protected; an older record without its evidence closure keeps R90's refusal. Worker selectors on an older evidence-closed record refuse `cleanup_worker_unavailable` because its current admission/report evidence is not documented. R148's sweep settles the explicitly requested delivery-recovery scope; a worker cleanup plan requires no sweep and closes no other objective. Undelivered lost work remains a lead task. The plan names only this objective's worktrees and branches and reads their native terminals, Git status, stashes, ancestry and remote tips; it classifies integrated, merged remote head, unique and protected resources. One scoped batched confirmation covers deletable classes, and an existing explicit instruction for the exact scope counts. Unique work is retained or archived and verified before ref deletion, unless separately confirmed for discard. Protected resources include the default and target branches, branches checked out in another worktree, remote branches this objective's Governor did not publish, and terminals not currently owned by a settled objective Dispatch. Rerun with `expect` immediately before deletion; execute only listed native/host guarded commands with ref leases, no automatic force or raw directory deletion. Native settlement and Delivery acknowledgment follow Orca; release is the coordinator’s explicit Orca step under R124, never automatic. PoD tick limitations remain report facts under R133; they grant no additional cleanup or lifecycle mutation.

The bound is 96 resources in one objective plan, including worktrees, local branches and Governor-proven remote branches. Repository discovery and cleanup stream the complete Git worktree inventory without a repository-wide count or byte limit. Cleanup retains this objective's paths and complete checkout observations for its branches, including unrelated worktrees sharing them; unrelated inventory size alone never refuses an objective plan. Read failure, incomplete inventory and uncertainty still refuse or protect. R113's independent full-registry guard is unchanged.

After consuming a worker or reviewer report and explicitly releasing that worker through Orca, the coordinator may request one worker's plan while the objective stays open. The optional `worker` object selects exactly one `admission` or `dispatch` from this objective. Its optional nonempty `reuse_reason` is at most 512 characters: save the returned plan as the reuse record, with that exact reason retained in `worker.reuse_reason` and the resource holds. This is read-only evidence, with no lifecycle write or automatic deletion. Native retention also preserves its exact `retainedReason`. Selection includes only the recorded placement, its local branch and matching branches this objective's Governor actually published. The integration worktree and a placement still held by another assignment stay protected.

Earlier admissions sharing the placement do not hold it forever: each must have a recorded report, fresh exact settlement and positive release proof, or belong to a recorded reuse chain ending at the selected released Dispatch. Every link in that chain has the same runtime, placement binding, native worktree and terminal. Transfer proof additionally requires the earlier readback's exact terminal resource to be released and owned by that selected Dispatch; missing ownership never proves transfer. Selecting an older reused admission still holds. An active, unreported, unknown, foreign or concurrent assignment holds the placement. These earlier observations and proof classifications also bind `expect`.

A worker plan needs a recorded report for the exact Dispatch, fresh exact assignment settlement and positive native release evidence. A present `terminalResource` must match the bound Dispatch owner, worktree and terminal and say `ownershipState: released` and `releaseState: released`. Supported older readbacks may omit `terminalResource`: their exact assignment's `projection.resource` must instead say `state: released` and `releaseState: released`. Both forms require the worker's exact recorded terminal handle, exited native liveness and no connected terminal; contradictory or incomplete identity stays protected. Active, unreported, unreleased, reused, retained, live, foreign and unknown resources hold with reasons; every existing dirty, ignored-data, stash, unique/archive, default/target/shared-branch, moved-after-delivery, fingerprint and remote-lease guard remains. Worker identity, release observations and the exact reuse reason bind the resource fingerprints, so `expect` cannot be carried to a different worker or retention decision.

After delivery the plan classifies against the current target while it still contains the recorded delivery result, as when later merges advanced it; when the target no longer contains that result, or the ancestry cannot be read, `moved_after_delivery` is true and every resource that depends on the target stays protected.

### R115 — Exact provider run binding

Type: B,H · Scenarios: [A285](#a285), [A286](#a286), [A287](#a287), [A288](#a288), [A289](#a289), [A290](#a290), [A291](#a291)

A Governor workflow row binds only a run its own effect could have started: one of its events, its exact head commit, created at or after its submission, and its own attempt. A publication-derived validation row, internally kind `workflow_dispatch` with `derived_from`, binds only a `push`, `pull_request` or `pull_request_target` run: a branch publication starts push runs and, on a branch with an open pull request, pull-request runs, and Pod cannot tell whether one was open. A run of another event, such as `workflow_dispatch`, `schedule` or `merge_group`, is never proof for that row. Requested dispatches and remote diagnostics bind only `workflow_dispatch` runs. These rows bind the run's first attempt. A validation rerun binds only the attempt provider facts prove its own. Before submitting, Pod durably records with the row the run, the latest attempt read just before and the submission start, and keeps them through every interruption and error; a rerun whose run cannot be read reruns nothing. Right after GitHub accepts the call, the row records that acceptance. One rule attributes a rerun's attempt on every path that reads one: execution's immediate read, readback, a reservation's outcome readback, a merge PASS's readback of its unit's effects and a carried row's readback. Attribution is proved by the count: Pod's accepted call creates an attempt, so when the row records that provenance (the submission start at full precision) and the acceptance, and the run shows exactly one attempt after the pre-read, that attempt is Pod's and no other actor's can be it. The attempt's start (GitHub's per-attempt `startedAt`) is only a contradiction guard, at the provider's precision: GitHub sets a rerun's start at the request in whole seconds, so the attempt binds when its start is not in a whole second earlier than the second containing the recorded submission start. Pod floors its own timestamp to that second only to match the provider's precision, never further. Every other state holds the row pending or UNKNOWN with a reason naming it: no recorded provenance, including an attempt an earlier Pod bound to a pending row without it, a caller-performed rerun reservation and any row recorded before this rule; no recorded acceptance (an interruption inside the call, or a lost reply), since a single new attempt may then be another actor's while Pod's own never landed; two or more new attempts; a start in a whole second earlier than the submission's, which contradicts the record whether another actor started the attempt or this host's clock and GitHub's disagree, or no reported start; and a recorded acceptance while the run still shows no new attempt, a contradiction that records no outcome. Only an unconfirmed rerun, with the exact run view showing no attempt after the pre-read once the call's time limit (120 s) and the 600 s absence margin have passed, reads FAILED with that reason, never no-effect. Pod's own earlier rows are never taken as the run's complete history. A held rerun is never resubmitted. Limitation: GitHub reports no requester per attempt and only whole-second starts, so a held rerun, including Pod's own attempt that appears in an earlier second through host clock skew, stays unsettled and blocks ordinary coordinator closure; R145 evidence closure preserves an unattributable result as UNKNOWN when delivery is proved, with no owner decision. Pod records the proved attempt with its event and reads that attempt by number afterwards, under the same rule; a later attempt, whoever started it, never settles the row. A run already bound to an unsettled row, whoever bound it, is verified exactly as a newly selected one: its event, head commit, creation at or after the submission and first attempt, and its exact workflow by appearing in the list GitHub filters by workflow file and commit, since a run view names only a display name. One that fails is kept as `rejected_run` (naming `head_sha` for a commit mismatch, or a `reason`) and never binds; one that cannot be verified holds; settled rows read as recorded. `gh run list --workflow --commit` filters on GitHub; each lookup states its scope, its limit of 20 runs, whether the list was truncated (the port asks for one run more) and that GitHub lists only the runs it retains. Missing or partial history leaves the row pending, or UNKNOWN, with that reason kept as its `readback` note: never FAILED and never proof of no effect. A truncated list settles and binds nothing, on every path, right after the list is read: readback, a bound run's verification even when that run is visible in the list, a landed publication's binding of its runs, execution's run lookup, a reservation's outcome readback and a merge PASS's readback of its unit's effects. An earlier Pod (0.12.0) loads these rows unchanged and ignores `readback`, `attempt` and `head_sha`; if it reconciles such a row it applies its own looser matching.

### R116 — Each outcome needs its own evidence

Type: H · Scenarios: [A292](#a292), [A293](#a293), [A294](#a294), [A295](#a295), [A296](#a296), [A297](#a297)

`governor-outcome` records only an outcome its evidence supports; otherwise it refuses `outcome_evidence_required` with a subcode and writes nothing. A row Pod performed (an executable kind without the decision-reservation marker, a publication-derived validation, or an unmarked older row) takes PASS, FAILED or CANCELED only from execution or `governor-reconcile`; by hand it records only UNKNOWN, without a provider receipt. A rerun Pod performs records its provenance before its effect and its acceptance right after (R115), so an interrupted rerun resumes by readback and is never resubmitted. Its own attempt is proved by the count, the single attempt after the pre-read once the acceptance is recorded, and its whole-second start is checked only for a contradiction at GitHub's precision; when R115's one attribution rule cannot prove its own attempt, including for a pending row an earlier Pod bound without that provenance, the row stays pending or UNKNOWN and blocks ordinary coordinator closure; R145 evidence closure preserves it without an owner decision when delivery is proved. A merge PASS keeps the caller's provider `merge_commit` and passes R93's Git checks at outcome time; the merge decision and each refusal say to fetch the target first. A merge FAILED or CANCELED needs the fetched target to lack the candidate's result: neither the candidate commit nor, within a bounded walk from the bound base, a commit with its tree. A release or deploy, performed by the project, takes PASS or FAILED only with a provider receipt or an evidence reference. A decision reservation's PASS or FAILED is what Pod's own provider readback shows; the caller adds evidence references only. CANCELED needs a `detail` attesting that the action never ran. For a reservation it also needs the row pending with no recorded sign of execution (a provider receipt, a bound or rejected run, a validation it started) and a readback from complete history that shows no effect; one predicate decides this and whether a helper offers "cancel, then execute". UNKNOWN never becomes CANCELED. An identical restatement answers from the record without a write, and another receipt for a recorded outcome refuses. Existing rows read exactly as recorded.

### R129 — Scope the required merge audit to its delivery unit

Type: B,H · Scenarios: [A371](#a371), [A372](#a372), [A373](#a373), [A374](#a374), [A375](#a375)

An assurance obligation may name an optional `unit` using the Governor's existing delivery-unit identifier form. Only assurances accept it; no unit need exist when the obligation is recorded. Its binding is immutable, including omission on an existing row, like kind, provenance and parent. Candidate remains the existing retargetable proof target and never supplies a unit binding. These are optional additions in the current record format, with no conversion.

For Governor purpose release, the required-audit gate selects non-withdrawn, not-gone project_policy assurances whose unit is absent or equals the action's unit. Only their gaps defer assurance_unbound, using the existing candidate/proof validator. A later unit's open, unadmitted audit therefore cannot hold an earlier unit's merge; its own merge still needs its audit. Every unbound assurance, including all pre-rule records, gates every unit. Single-unit decisions, deferral codes and journal rows stay identical to 0.15.0. Publication/validation and optional assurance retain their earlier rules.

Only the assurance gate narrows. The separate integration_unsettled release gate still waits for every outstanding objective assignment, including another unit's running audit. The objective-wide independently reviewed label (R88) and final acceptance still require every non-withdrawn assurance.

### R144 — Closure is part of delivery

Type: B,H · Scenarios: [A456](#a456), [A457](#a457), [A471](#a471)

As soon as the source's PoDs are all ticked, delivery is merged and installed where in scope, and the final report is consumed, the coordinator records closure in the same turn, before it may end, be released or have its tab closed. R117 supplies recording order and the ordinary closing checks; closure needs no additional owner decision. A verified delivery's closing checkpoint keeps the trusted governance baseline under R147, adopts no changed policy and records that it did not adopt even when the target moved past that delivery: the closing write's answer carries `governance_adoption` and the stored governance base stays at the trusted baseline.

A delivered objective's closing write is not held by a publication-derived validation row (kind `workflow_dispatch` with `derived_from` a publication, carried rows included) whose commit is an earlier head of a delivery pull request that merged with a different head. The closing write proves the delivery as R145 does (source and every delivery pull request over the chain, read at that write) and reads the pull request's commits. It reads the row back read-only first: a row that would settle refuses the closure with `governor-reconcile` as next action. Otherwise the closure records it under `closure.preserved` with outcome UNKNOWN and reason `superseded_by_merged_head`, naming the pull request and merged head, and the journal stays byte-identical. Nothing is stamped. A zero-run listing alone never suffices. These keep today's refusal until the existing reconcile or accounting settles them: a derived validation of the merged head, every requested dispatch, rerun, diagnostic, cancellation, push and pull-request update, merge, release and deploy rows, a row whose supersession cannot be read, an unconsumed report, and an unproved or unverified delivery. The refusal names the proof's conditions and each held row. Status stays record-only (R114). Readiness names the coordinator next with a summary starting `Delivered, not closed:` while only such derived validation rows and closure remain. Its next action is to reconcile each row or write the closing checkpoint, which performs this check. The closing write's acknowledgement and refusal name rows `preserved_at_closure`.

When the objective is delivered under the existing delivered test and R117 has only `closure` remaining, R114 readiness is `finalizing`, `acts_next: coordinator`, `coordinator_needed: true`, even with recorded owner or user waits. Its summary starts `Delivered, not closed:` and says the coordinator records closure now and no owner decision is needed. A lost coordinator instead takes R145's evidence closure through R148's sweep.

## Acceptance scenarios

- <a id="a81"></a>**A81** — A superseded candidate and premature validation each defer with an explainable reason and next action; an identical running action is attached to and a passing result with the same exact proof identity (candidate and context, workflow, triggering event and dispatch inputs) is reused; a necessary rerun after changed input proceeds.
- <a id="a82"></a>**A82** — A scoped Governor efficiency exception affects only efficiency deferrals, never authority or correctness.
- <a id="a83"></a>**A83** — Push/PR or another remote validation kind without exact `publish` authorization and merge without exact `merge` authorization defer before effects; wrong candidate, tree or scope never grants either action. Technical readiness remains separate from permission.
- <a id="a84"></a>**A84** — Several locally discoverable corrections in one delivery unit converge on the same branch and pull request; no intermediate correction crosses the remote boundary until its candidate passes the configured local preflight.
- <a id="a85"></a>**A85** — Two callers requesting identical validation concurrently produce one admitted execution; the other attaches to it.
- <a id="a86"></a>**A86** — A submission whose response is lost stays UNKNOWN, blocks a resubmission, and is settled only by provider readback; after a coordinator restart the unit's candidate bindings, evidence, decisions and pending effects remain recoverable.
- <a id="a87"></a>**A87** — A changed source, base, workflow, environment or policy opens a new candidate generation, and evidence bound to the previous one is not reused as current proof even on the same commit.
- <a id="a88"></a>**A88** — A remote-only question admits a bounded diagnostic naming its question, local limitation, check and stopping condition while the candidate is still converging, without pretending the candidate is release-ready; an unchanged repeat is answered from the record.
- <a id="a89"></a>**A89** — An unclassified remote failure is not retried; a code defect is recorded as a correction, and the third equivalent correction requires a diagnosis with distinct bounded evidence before validation resumes.
- <a id="a90"></a>**A90** — Supersedence cancels a pending, cancel-safe validation of the old candidate only when policy allows it, its result can never approve the newer candidate, and a pending deployment is never canceled by supersedence.
- <a id="a91"></a>**A91** — An independent or urgent delivery unit is admitted while another unit's workers, deliveries or corrections are unsettled.
- <a id="a92"></a>**A92** — A project file that relaxes Governor mode, widens retries, enables cancellation, declares host control or adds an exception is refused.
- <a id="a93"></a>**A93** — The enforcement level is reported as advisory unless the owner's personal policy declares a host control, and it is never reported as a proven control.
- <a id="a164"></a>**A164** — With no applicable consent, the coordinator shows repository, target, candidate commit/tree and `publish`/`merge` scope once; remote merge choice records both scopes, permits push/PR and required CI, and merge uses `--match-head-commit` for that exact candidate without a second routine check prompt.
- <a id="a165"></a>**A165** — Local-only revision creates no `publish` or `merge` authorization: push, PR update, workflow dispatch, rerun, remote diagnostic, cancellation and merge defer before effects, while hosted checks appear as `NOT_RUN`; defer records `user_hold`.
- <a id="a166"></a>**A166** — Changing the prepared candidate/tree or target after consent makes the former authorization unusable; a new exact decision is required. Deployment, new provider effects and spending are not enabled by delivery consent.
- <a id="a167"></a>**A167** — For exact merge, squash and fast-forward commits with the authorized tree and target, an allowed merge PASS plus matching provider readback stores one delivery record and permits closure without governance refresh or proof rebind.
- <a id="a168"></a>**A168** — A missing/other-objective record, wrong scope/candidate/tree, wrong remote or target alias even with equal SHA, a merge naming another target than its prepared unit, rebase result, readback mismatch or second different record refuses `delivery_unverified` or `delivery_recorded` without a write.
- <a id="a169"></a>**A169** — When the target moves after a verified delivery result, including when the same record is restated or first recorded late, a non-closing checkpoint's currency refuses `governance_changed` and names a direct user decision for the new exact snapshot; candidate-authored policy is not adopted.
- <a id="a478"></a>**A478** — Through real Governor and outcome operations on synthetic baseline A, first delivered result B, candidate C on B and result M with parents B and C, the second merge settles PASS after first delivery by merge, squash or fast-forward. Its policy binding and the one delivery record keep A; its target binding commits to B. Second squash and fast-forward results use that same admitted operational parent.
- <a id="a479"></a>**A479** — A stale or unavailable target, this objective's landed merge without a verified delivery record, a prepared target ref unrelated to governance even at an equal commit, and a target moving during admission each refuse before any journal/context write or relayed-consent consumption; a relayed merge consent refused this way is still unused, and the unrelated target names preparing the unit again.
- <a id="a480"></a>**A480** — An admitted target commit must be a full object id; a present invalid value never falls back to recovery. A result on a later parent refuses without a write, says the target may have moved or the merge rewrote commits, that a snapshot decision cannot settle the row and that it stays UNKNOWN with its evidence; FAILED and CANCELED still refuse for the landed result. Changed candidate, authorized or Git tree, and authorization still refuse. A carried copy settles only from its provider readback using its copied admitted parent.
- <a id="a481"></a>**A481** — A synthetic 0.21.1-shaped row first fails its original policy-base check, then settles PASS only through the eligible map-delivery recovery at governor-outcome. ### R136 — Record a standing authorization ("yolo") for one objective

Type: H · Scenarios: [A429](#a429), [A430](#a430), [A433](#a433), [A434](#a434), [A435](#a435), [A436](#a436), [A438](#a438), [A441](#a441)

The owner may put one objective in yolo mode by recording a standing authorization, an owner decision of its own kind that the Governor applies to each exact candidate as it comes (R137). While it is active, the coordinator does not wait for the owner at the effects it covers. It removes only the wait for consent: it is not blanket permission, and no Pod gate changes.

The objective context holds one append-only `standing_authorization` record, `pod-standing-authorization/v1`, with at most 32 `decisions` and at most 16 responder `answers` (R138). Each complete stored decision, including its full verifier verdict, is limited to 4096 encoded bytes: compact sorted-key UTF-8 JSON plus its final newline. The shared text limits still apply, including 1024 characters for `instruction`; the encoded byte limit may require shorter text or relay metadata. An oversized row refuses `invalid_standing_authorization` before consuming a receipt or writing context. The 32 decision rows and 16 answer rows together use at most 256 KiB, plus at most a 512-byte record envelope, of the 512 KiB context limit; closure also needs its projection and ordinary checkpoint/report space under R121. Closure uses compact standing decision references and responder text prefixes, rather than copying full verdicts and answers. The A439 maximum-history fixture includes 64 effects and 64 KiB of ordinary question context; its exact closure budget is stated there. With that fixture's target and effect shapes, standing history is 262382 bytes including its closure time, and the closure report is 58807 bytes (5965 bytes of standing owner-decision references, 52471 bytes of standing projection). The complete closed context with 66926 bytes of ordinary question context is 391415 bytes, leaving 132873 bytes of the 524288-byte limit. This is a measured fixture budget, not a guarantee for arbitrary checkpoints or longer effect metadata; every closing write still obeys R121. A capacity warning identifies the standing section as bounded and needing no maintenance; report triage cannot shrink it.

A decision uses R120's shared validator (`provenance: user_direct`, `instruction`, optional `channel`, and `relay` exactly when relayed) and adds a Pod-assigned `id` (`Y1`, `Y2`, ... in order), an `operation` (`activate` or `revoke`), `utc` from Pod's own clock, never from the caller, and the map `seq` current when it was recorded. A session decision's decision time is Pod's clock when recorded. A relay uses its verified `decided_at`, distinct from Pod's receipt time (`utc`). An otherwise authentic, fully verified and exactly bound future-dated activation refuses `standing_authorization_future` without changing objective context or journal or creating an authority row. Its key is permanently marked refused in the existing relay receipt store; every later use refuses `relay_authorization_reused`, even after a stop and after Pod's clock passes `decided_at`. This narrow receipt write never overwrites an accepted, interrupted or refused receipt; forged, mismatched, unverified and malformed inputs write no receipt. A fresh owner decision with a new key remains possible. A future activation is never clamped into a grant. A verified future-dated revoke uses receipt time as a conservative stop barrier and can only reduce authority. Its row retains the original verified `decided_at` and `utc`; status history's `decided_at` is the capped ordering time. The full verdict is preserved. Recording order never substitutes for decision time.

The record also holds `observed`, Pod's latest matching read of the bound source (below), the required `observed_scope_digest`, optional latest `closed_at` and `reopened_at` facts atomically stored with their checkpoint, and one required monotonic authority barrier, `not_before`. That barrier rises to the decision or event time of every recorded activation or revocation, every received stop even while yolo is off, and every closure and reopen of a record holder. While the record exists, `observed_scope_digest` holds one observed material identity, decided at each record write against the checkpoint being written: the material scope digest when Pod's latest read (`observed`) is of the current bound source, and otherwise an unread identity of that bound source (its source digest with the criteria), because Pod cannot attest a body it has not read. Every change of that identity raises the barrier to the write time, so an unread changed source is itself a transition and fails closed. Learning the body of that same, previously unread bound source is not a transition, and Pod's own confirmed tick (R131) carries the observation to its rebound source because it flips one checkbox. This includes a record created by a stop while off, with no activation. Repeating an identical observation does not move the barrier. Every relayed activation independently uses the exact digest binding below. A mismatch with the latest activation also records its bounded id in `scope_changed_for`, keeping suspension sticky through restoration: restoration is not owner confirmation, and an older matching relay stays stale after any intervening observed change. A new activation clears the marker. When a change is first observed during a relayed activation's own live read and that relay confirms exactly the newly observed digest, that observation does not make the relay stale; it records the digest without raising a later barrier. Prior recorded barriers still apply and are never erased by that read.

There is one content-identity limit, only for an objective that genuinely never held a standing record: preserving its 0.18.0 shape leaves no usable history of an intermediate material revision. A verified first activation naming exactly the restored content the owner confirmed may be accepted after A/B/A, under the remaining ordering rules. When that first verified relayed activation creates the genuinely never-existing record, the record also starts at its receipt: the barrier rises once to that receipt time, a distinct admission fact (the row keeps its verified `decided_at`). Other relayed activations decided before the record existed then refuse `standing_authorization_stale` and need a fresh owner decision, the conservative cost of this limit. Later decisions keep owner decision-time ordering, and a stop still compares with the activation's actual decision time and wins ties. The host must have saved that digest with the actual owner decision; it cannot echo a later request or substitute another scope. This proves content identity, not absence of intermediate revisions. It never covers a stop-created record without an activation, known prior standing history, invalid or lost records, or an untimed earlier reopen. Missing or malformed history refuses; recover the existing record rather than claiming the never-record exception. When a new confirmation is needed, obtain a fresh owner decision for the current digest or use an actual coordinator-session activation; the path with an unavailable reopen time still requires that session activation. Stop, closure, expiry, refused-key and host protections remain independent. These bounded facts survive the eight-row reopen history and add no second journal. Closure and reopen without the record create no standing record or new channel discriminator. An activation also records:

- `scope`: a nonempty set of `publish`, `merge`, `release`, `install` and `cleanup`; all five when omitted. `deploy` is in scope only through a widening.
- `widening`: the exclusions the owner explicitly removed, by name; none by default. Naming `deploy` also adds it to `scope`, as in "yolo including deploy".
- `exclusions`, computed by Pod: `deploy`, `paid_resources`, `secrets`, `unique_deletion` and `scope_growth`, minus the widening. Each keeps its normal owner question: production deployment, new paid or cloud resources, secrets, deleting unique or unmerged material, and work beyond the objective's scope. Pod enforces only `deploy` (outside the scope), a merge that names no pull request and unique material in cleanup mechanically (R137). It records and shows the other exclusions, and the coordinator keeps asking the owner about them.
- `expires_at`, optional: a zoned timestamp later than now, stored in UTC.
- `binding`, computed by Pod: a digest of the objective's scope, which detects a material change (below). It covers the bound issue's repository, number, locator and amendments, the issue body with every task-list checkbox marker (`[x]` or `[X]` at the start of a list item) normalized to `[ ]`, and the criteria. A direct objective's binding covers its criteria only.

The owner turns it on at any time:

- At start, the owner types `/pod <link> yolo`. The coordinator records the activation right after intake and before any admission.
- Later, the owner types a plain instruction in the coordinator's own session, such as "use yolo from now on". The coordinator turns it into the exact decision (scope, widening, expiry) and records it with `channel: session`. Text an executor, a host agent or a mailbox relayed is `relayed`, never session (R120).
- A relayed activation is accepted only when the host verifier's `standing` action confirms exactly this objective, operation, scope, widening, expiry and material `scope_digest` (R139). The request carries `standing.scope_digest`, computed after the activation's own live issue read, equal to the digest Pod would bind now. The host must compare it with the digest saved with that exact owner decision; echoing the request is not verification. A different, missing or unknown decision-time digest refuses `relay_verifier_mismatch` naming `standing.scope_digest`, before key use or a write, with a next action to obtain a fresh owner decision for the current digest. This includes release and, only with an explicit owner widening, deploy; it authorizes no deploy target by itself (R120). Pod stores the complete verdict, takes `relay.owner_source` from it and consumes its `single_use` key for one row. Without a configured verifier it refuses `relay_verifier_unconfigured`; other verifier failures reuse the existing relay codes. A verified relayed widening may name any default exclusion: `deploy`, `paid_resources`, `secrets`, `unique_deletion` and `scope_growth`, each explicitly, under the same exact binding. It never confirms Password Manager Defaults, authorizes DRAINED/REPLACE/reboots, bypasses secret handlers or disables gates. Widening never bypasses the scope binding or suspension.
- An activation of an issue-bound objective reads the bound issue live through the existing issue recheck. A live body that differs from the bound digest, an unreconciled edit, refuses `issue_reconciliation_required` without a write; reconcile first.
- An activation made while one is active replaces it, which is how a later widening or narrowing is recorded. One made while suspended is the owner's re-confirmation.
- Activating restarts and reopens nothing. A consent wait that deferred `authorization_missing` is satisfied at the Governor's next check.

"Stop yolo", typed in the session or verified-relayed, always raises the barrier. It ends yolo unless its decision time is strictly earlier than the latest recorded activation's decision time; a tie keeps the stop. On an active verification path, a stale stop refuses `standing_authorization_stale`, records no decision row and leaves the state. A revocation row is accepted whenever the state is `active`, `suspended` or `expired`. While off, a stop reports the current state without a decision row or key consumption, but persists its barrier, creating the record if needed. A no-op relayed stop verifies its `decided_at`; if verification is unconfigured or fails, the barrier uses Pod's receipt time as a fail-safe. When verification fails while yolo is on, Pod preserves the honest verifier refusal and current state, but raises `not_before` to receipt time, with no decision row or unverified key consumption. A genuinely newer verified decision can still follow. Recorded-key reuse refusals remain unchanged. Objective closure ends an activation permanently; reopening keeps it ended until a new owner activation.

A verified relayed activation must not be future-dated and is accepted only when its decision time is strictly later than `not_before`; otherwise it refuses `standing_authorization_stale` before consuming its key or writing anything. Its verified material digest must also match the current digest, even before any activation, after a second scope change, or after a stop while off. The receipt-only interrupted-write completion obeys the same predicate. Stale and future refusals precede the history-cap check. A session activation is recorded now, after the barrier. A genuinely newer relay remains acceptable when an older relay was recorded late. An objective reopened before it first held the record has no trusted reopen time: genuine 0.18.0 rows kept none. A relayed activation then refuses `standing_authorization_stale` with reason `reopen_time_unavailable` and the next action to activate in the coordinator's session; after that activation, newer relays work. This preserves never-yolo readability without inventing earlier times. Ordering assumes the verifier's clock and Pod's clock agree; a slow verifier clock can still misorder decisions.

The record keeps at most 32 decisions, and the last row is reserved so that a revocation always fits: an activation refuses `standing_authorization_full`, writing nothing, when the record already holds 31 or more decisions. Nothing is evicted, so the history stays complete.

One function of the record and the objective context gives the state, used by every reader; the mode is `yolo` only in the state `active`:

- `none`: no decision. `revoked`: the latest decision is a revocation.
- `ended`: the objective is closed, continued by a successor claim or under historical retirement (R112), or its latest standing decision predates a recorded reopen.
- `expired`: the latest activation's `expires_at` has passed.
- `suspended`: Pod cannot show that the objective's scope is the one the owner confirmed. Reason `scope_changed`: Pod's latest observation of the bound issue body, with the current amendments and criteria, gives a digest different from the activation's `binding`. Reason `scope_unobserved`: the objective's current bound source is one Pod has not observed (the source digest differs from `observed`), so a stale binding is never hidden. Any change of body text other than checkbox markers, of the amendments or of the criteria is material, and Pod cannot judge wording, so every such change counts. Checkbox-only edits, including a tick Pod itself wrote (R131), are not scope, and a metadata-only issue edit changes no digest. A material change ends only when the owner activates again; `scope_unobserved` also ends when a later Pod read shows the scope unchanged.
- `active`: otherwise.

Whenever Pod itself reads the bound issue body for the objective's current source and it matches the bound digest, which happens at an activation, at a reconciling or introducing checkpoint and at a tick's readback and rebind, an objective that holds the record stores `observed`: the current source digest and the body scope digest. Its `observed_scope_digest` tracks the observed material identity across those observations and context writes, including criteria changes in a direct objective; a read records only `observed`, and the transition is decided at the following record write. An objective without the record gains no field. Explicit standing `show` reads a short locked snapshot, releases the lock for its bounded live issue read and digest calculation, and rechecks the snapshot under the lock. A concurrent context change returns an unknown digest and a retry action (R139); show stores no observation and never moves a barrier.

Yolo belongs to one objective. A successor claim, a continuation or another objective never inherits it, and the record is not copied; the owner turns it on there if wanted. Runtime continuity and owner handoff of the same objective keep it. A carried Governor row (R118) authorizes nothing new. A host stop halts work as before. Pod records no host-stop state and adds no stop detector. A host whose stop is meant to end yolo must turn that stop into a verified relayed revocation (verifier action `standing`, operation `revoke`) for each objective with yolo on, before work resumes, so a resume can never silently restore a standing authorization from before the stop. Pod provides only that verified revocation path; the host's side is its own and stays NOT_RUN until the host proves it, and Pod fixtures never establish it.

`pod internal standing-authorization` writes the record. It needs the recorded coordinator with current native authority, writes under the context lock without a map seq (like a constraint) and refuses a closed objective, a continued one and one under historical retirement with the existing codes `objective_closed`, `objective_continued` and `objective_retired`. Malformed input refuses `invalid_standing_authorization` with the record's bounded fields and writes nothing.

- a merge names no `pr`;
- the unit has no prepared binding or target;
- the state is not `active`.

After revocation, suspension or expiry it is MISSING, and an authority wait for that scope and candidate is accepted. The wait validator uses the state being checkpointed, so suspending yolo and recording the wait in one write is accepted.

The scopes `install` and `cleanup` have no Governor action. `install` lets the coordinator perform the stated post-merge installation and verification (R59) without asking. `cleanup` is applied by `internal cleanup-plan` (R94): with an active record that has `cleanup` in scope, the plan lists integrated worktrees and branches and merged remote heads as covered, lists unique material as asking unless `unique_deletion` was widened, and never covers protected resources.
