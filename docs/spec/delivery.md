# Delivery

## Requirements

### R54 — Project governance owns source selection, checks

Type: H · Scenarios: [A09](models/preferences.md#a09), [A35](coordination.md#a35), [A68](assurance.md#a68)

Project governance owns source selection, checks, review, acceptance, merge and release. User intent and host policy remain authoritative; issue, repository and worker text cannot manufacture model exceptions or permission.

### R58 — Before Pod-mediated remote action, return explainable

Type: B · Scenarios: [A81](#a81), [A82](#a82), [A164](#a164), [A176](coordination.md#a176), [A187](#a187), [A188](#a188), [A189](#a189), [A190](#a190), [A191](#a191), [A222](#a222)

Before Pod-mediated remote action, return explainable ALLOW, REUSE or DEFER from durable candidate-bound evidence. Push, pull-request update and every other remote validation, diagnostic or cancellation effect require `publish` authorization for the exact commit and tree; merge requires `merge` authorization and names the prepared unit's target. Duplicate action attaches or reuses proof. Decision-only ALLOW reservations of executable kinds are marked and explain caller execution or cancellation before managed execution; execute-created and other rows are unmarked. Validate workflow effects/targets and the `pull_request` input (R240's keys only) before journaling or effects. A landed push remains PASS on observation failure, updates published state and proceeds to the PR step; unreadable PR lookup remains UNKNOWN without blind creation and reconciles from branch head. Workflow-dispatch validation proof comes only from an exact run: its proof identity is its candidate, context and workflow plus the triggering event and dispatch inputs, and Pod's own readback must show a `workflow_dispatch` run before a PASS counts; a remote diagnostic keeps its 0.6.6 reuse. A run from another event, with other inputs or with an unknown event is not proof; the request proceeds when the other checks pass, and a failed run on the same key still gates it. A failed run's failed jobs are rerun within that same run; job results are never combined across runs. Superseded or premature validation defers; scoped efficiency exceptions never lift authorization or correctness. Same-candidate read-only review may overlap validation, while release waits for both.

### R92 — Delivery decision

Type: H · Scenarios: [A164](#a164), [A165](#a165), [A166](#a166), [A186](#a186), [A386](interface.md#a386)

Before the first remote Git mutation, obtain the one three-way delivery decision in R59 unless exact applicable authorization already exists. A `publish` authorization binds push/PR, workflow dispatch, rerun, remote diagnostic and cancellation to the prepared candidate commit and tree, and `merge` binds merge to that same pair and the unit's prepared target. Both retain the stated continuation; candidate or target movement invalidates consent. While a standing authorization (R136) is active and its scope covers `publish` and `merge`, it answers the three-way decision as merge remotely for each exact candidate, without a new prompt; an explicit authorization on the request takes precedence (R137). Release-purpose admission preserves non-withdrawn project_policy audits bound to its delivery unit and unbound audits as R129 specifies, using existing candidate proof validity; missing/invalid proof defers with correctness `assurance_unbound`. Scoped waivers/trusted source removal remain distinct from passing review, while publication/validation can overlap required review and optional coordinator assurance gains no new gate. Status and authority-wait readers use the same applicable-target truth: an unbound/missing unit has no applicable merge consent even with an older target-less row. Actual merge refusal remains unchanged. Local-only and defer authorize no remote effect, and routine post-merge checks do not create a separate approval step. R131's bounded PES checkbox edit uses OD-5 standing authority and is not a publish or merge effect.

### R93 — Verified delivery record

Type: H · Scenarios: [A167](#a167), [A168](#a168), [A169](#a169), [A478](#a478), [A479](#a479), [A480](#a480), [A481](#a481), [A482](#a482), [A789](#a789), [A962](#a962), [A1025](#a1025), [A1026](#a1026), [A1027](#a1027)

A merge request is ready only when the candidate PR head contains the current bound target commit. Before allowing a merge, the Governor checks ancestry against the exact target commit it binds. Missing or unproved containment returns correctness DEFER, naming the target ref and commit and directing the coordinator to merge or rebase that target into the candidate, then re-review the affected scope under the existing rules and prepare the new candidate. Neither observe mode nor an efficiency exception can allow it. This readiness check leaves the outcome rule unchanged: the result tree must equal the candidate tree.

After an allowed merge lands, fetch its target and record the merge PASS with its provider `merge_commit` through `governor-outcome`, which applies these checks then (R116), then checkpoint `delivery: {record}`. Verify this objective's record, `merge` authorization, candidate/tree, canonical target identity and exact merge, squash or fast-forward result with matching tree and readback. The target is the one admitted with the merge decision; the action and its `merge` authorization name it as `<remote>/<base>`. A mismatch refuses `delivery_unverified`; outside R154's completion-only route, a moved target requires a new direct user snapshot decision when recording or restating delivery. A later close: true checkpoint or report may use R154's shared completion-proof route, including its GitHub-linked alternative; that alternative creates no R93 verified delivery record. Closure retains its trusted baseline without governance_refresh or an owner snapshot decision and adopts no changed policy (R144, R147). R154 also permits a delivery-only verified write on the same retained baseline; other recording or restatement never skips currency, and a delivery result stays current only for the base and target it was verified against. Store one idempotent record. A later delivery of the same objective replaces it only when its record is this objective's allowed merge PASS on the same target, of the checkpoint candidate, which differs from the recorded candidate; when its journal row comes after the recorded one and finished after it; when its result contains the recorded result; and when it passes every check above. Any other different record refuses `delivery_recorded` with its reason, and the record is unchanged. The superseded merge action remains in the Governor journal. Retain the trusted governance baseline and valid existing proof without refresh or rebind. Candidate-authored policy gains no authority. A host-verified local append is a separate delivery kind (R209): it never satisfies, settles or replaces this record, and this record never replaces it. The status `governance_stale` observation, never a gate, compares current governance with the newer governance basis: this record's result while governance still carries the base and target it was verified against, otherwise the bound base, so a later governance refresh to current main reads current and a target that moved after it reads stale.

The policy base, observed target and admitted merge parent are distinct. Before a
merge admission writes any journal or consumes relayed consent, its prepared target
must be the governance `base_ref` and its currently resolved commit must pass the
same currency predicate as other governed work: the policy base, or this objective's
verified delivery result for exactly that base and target. Otherwise refuse without
a journal or context write; an unrelated prepared target names preparing the unit again
on the governance target. Record that exact observed commit as
`target_binding.commit`; retain the policy base in `governance_binding.base` and in
any delivery record. A second delivery may therefore merge from the first verified
result without adopting its policy. It creates no further currency exception:
recording it replaces the delivery record, and currency then follows the new record.

When `target_binding.commit` is present it must be a full object id. Verify parents
against that commit: merge parents are exactly `[commit, candidate]`, squash parents
exactly `[commit]`, or a fast-forward result equals the candidate with that commit
an ancestor. Every candidate, tree, authorization, target and provider readback check
still applies. A carried row uses its copied target binding under the same rule.
Other parents refuse `result_not_exact`: the result is not an exact merge, squash or
fast-forward of the admitted commit (the target may have moved after admission or the
merge rewrote commits), a new snapshot decision cannot settle the row, and the next
action keeps it UNKNOWN with its merge evidence. FAILED and CANCELED
still refuse when the target contains the landed result; neither an arbitrary
descendant nor a new snapshot rewrites an admitted merge.

Earlier rows without that commit first use their original policy-base check.
Only `governor-outcome PASS` may recover a failing parent check using this
objective's map delivery result, when the row is not carried, the delivery names a
different ALLOW merge PASS row in this journal, that row's zoned receipt
`finished_at` is at or before this row's admission `at`, the delivery base equals
this row's admitted policy base, its target ref equals this row's target ref, and
every other R93 check passes. No other path infers a recovered parent. Recovery
adds a kernel-owned row `parent_basis` with `commit`, `basis: verified_delivery`,
`delivery_record`, `admitted_base`, `observed_at_admission: false` and `prior`, returned
in the outcome acknowledgement. `prior` is null for a pending row; for an UNKNOWN row
it keeps that outcome and its recorded `finished_at`, which settlement replaces. The
marker is separate from `target_binding` and cannot be caller-supplied. Never rewrite
the admitted bindings, decision, authorization or existing provider evidence or
detail: a recovery whose provider fields or detail would replace recorded ones, compared
as JSON values so that `1` and `true` differ, refuses
`receipt_recorded` without a write. Subsequent checks use the recorded recovery basis.
Ineligible earlier rows keep their refusal and unchanged state. When the row has an
admitted governance binding or is carried, its base is immutable, so the refusal says
a new snapshot decision cannot change it and keeps the row UNKNOWN with its evidence;
only a row without either binding keeps the snapshot-decision next action, because an
owner refresh changes the base it is checked against.

### R234 — Settle an unexecuted merge decision superseded by a later same-PR merge

Type: B,H · Scenarios: [A1039](#a1039), [A1040](#a1040), [A1041](#a1041), [A1042](#a1042), [A1043](#a1043), [A1044](#a1044), [A1045](#a1045)

An earlier pending or UNKNOWN ALLOW merge decision settles as `superseded` when a later ALLOW merge PASS in the same objective journal proves the same PR merged at a different exact candidate head on the same admitted target. The earlier row has no recorded execution evidence and is not carried. Verify the later result under R93 with its recorded provider merge commit, using local Git only. Require the earlier admitted parent to precede the later admitted parent, the old head to be absent from the later admitted target, and a complete bounded first-parent walk from the result to the earlier admitted parent showing that the old head was neither a target commit nor a merge head. For a verified fast-forward, walk from the later admitted target rather than the candidate, whose first-parent ancestry is not a record of earlier target heads. An old head contained within the refreshed candidate alone does not show execution. Missing, conflicting or over-limit proof leaves the earlier row unsettled.

Store `superseded_by: {record_id, merge_commit}` on the earlier row, naming the replacing decision and exact merged result. Preserve its admitted bindings and receipt evidence, provider fields and detail. The terminal outcome removes its pending/UNKNOWN closure hold without declaring that merge executed. Recording the newer merge PASS settles qualifying earlier rows; explicit `governor-outcome superseded` and `governor-reconcile` support recovery without provider readback or remote effect and repeat idempotently. Every other outcome's rules stay unchanged: an earlier head that actually merged still settles PASS, and uncertain execution, carried rows and other action kinds gain no new settlement route.

Before a new merge decision for a different head of the same PR and target, an earlier non-carried pending or UNKNOWN ALLOW causes correctness DEFER `prior_merge_unsettled`, with a next action naming the exact earlier decision and the `pod internal governor-outcome --input FILE` request: CANCELED for pending with a never-executed detail, FAILED for UNKNOWN, subject to their existing checks while the PR is open. Carried rows retain their existing admission and readback rules. No new ALLOW is recorded until that settlement. Earlier histories containing both decisions retain the recovery path above.

- <a id="a1039"></a>**A1039** — Synthetic earlier history: ALLOW A, refresh to B, ALLOW B, exact merge B and its PASS settle A as superseded with replacement decision and result; A remains an ancestor inside B, no provider readback occurs and delivery and closure proceed.
- <a id="a1040"></a>**A1040** — A merge whose head is A still records A PASS under R93 and cannot become superseded.
- <a id="a1041"></a>**A1041** — A new same-PR merge decision for B defers while A is pending, names settlement before replacement, and allows after A is validly canceled while the target lacks it.
- <a id="a1042"></a>**A1042** — An earlier UNKNOWN A settles from newer verified same-PR merge B while preserving A's earlier receipt detail and evidence.
- <a id="a1043"></a>**A1043** — Both explicit superseded outcome and reconcile recover an earlier qualifying row without a provider read; exact repeats leave journal bytes unchanged.
- <a id="a1044"></a>**A1044** — Other PRs, missing later verified PASS, recorded execution evidence, carried rows, unverified merge results and old heads already merged or in target history cannot establish supersedence; failed requests leave the journal unchanged.
- <a id="a1045"></a>**A1045** — Installed Governor guidance explains settlement before a refreshed merge decision and local recovery of an earlier superseded decision, without changing executed-merge settlement.

### R240 — Keep an existing pull request's text current

Type: B,H · Scenarios: [A1077](#a1077), [A1078](#a1078), [A1079](#a1079), [A1080](#a1080), [A1081](#a1081)

When managed `pr_update` reuses the open pull request of its branch and base and the request supplies `pull_request` text, Pod brings the supplied fields (a nonempty title, a body when given) to that text after the landed push, inside the same admitted row: the same publish authorization and candidate binding, with no new authorization scope. The edit is a second mutation, so right before it Pod rechecks that the objective is still owned and its governance current, that the unit's prepared candidate is still the row's (clean, and the authorization's commit and tree), and every decision as at the push without consuming its single use again: a standing decision in full, a decision-bound grant through its non-consuming reuse (current candidate, identity, policy and the original vouch), and a relayed decision by a fresh verifier verdict that must equal the recorded one. A failed recheck writes nothing (`held`, naming its code), and the relay receipts are unchanged either way. It first reads the pull request fresh (`gh pr view N --json number,url,state,headRefName,baseRefName,title,body`) and writes with `gh pr edit N [--title T] [--body B]`, both exact allowlisted shapes with the existing bounds (title up to 256 characters, body up to 16 KiB). The row's provider records `pr_text`: `status`, the written `fields`, and SHA-256 digests of the `requested`, `before` and `after` text, each taken after normalizing line endings to LF and nothing else, since other whitespace (an indented code block, a trailing line break) can carry meaning. A title or body that is not valid Unicode text (a lone surrogate) refuses `invalid_pull_request` at admission, before any record or effect. Opening a pull request is unchanged and records `status: opened` with the digests of the text it wrote, so a later publication can tell its own text from another writer's.

Pod overwrites only text it wrote itself. A requested field whose current digest differs from the requested one and is not the digest Pod last recorded for that field of that pull request in the objective's journal (opened, updated or unchanged; after an unconfirmed update, exactly the text read before it and the text submitted, which replace the field's earlier baseline) is another writer's: a person's edit, or text Pod never recorded, such as a pull request opened by hand or by an earlier Pod. Pod then writes nothing and records `status: conflict`, `decision: lead`, the `edited` fields and the `before` digests, and the row's detail says the lead decides. The lead keeps that text by publishing without the field or with the same text, or replaces it by publishing a later head with `pull_request.replace_edited` set to exactly the recorded `before` digests; Pod writes only while the fresh read still shows them, and records the overwritten fields as `replaced`. Equal text writes nothing (`unchanged`). An unreadable read, one showing another number, a closed pull request, another head or base, or text that is not valid Unicode writes nothing (`unread`); an edit whose confirmation was lost or whose answer broke the port's contract is `uncertain`, and one refused before submission is `failed`. Any ordinary fault inside the text step is recorded as `unread` with its class or code and never takes back the landed push, the reused pull request or its derived validation; only an interruption propagates.

The text step never changes the row's outcome, its publication facts or derived validation: the push and the reused pull request are proved as before, and a row with no supplied text, a pull request Pod opens, a merge, delivery record and every readback behave as before. A readback that settles a lost publication records no text step. The same candidate published again remains REUSE and writes no text. An edit triggers only workflows that listen to the pull request's `edited` type, which the existing `pr_update` trigger accounting covers. Limitation: GitHub has no conditional pull-request update, so an edit between the fresh read and the write is overwritten; an interruption after the write and before its record leaves the next publication reporting a conflict for the lead.

- <a id="a1077"></a>**A1077** — Opening a pull request issues the same push, lookup and create as before and records `pr_text` `opened` with the digests of the supplied text, or of the action's reason title and an empty body when none is supplied.
- <a id="a1078"></a>**A1078** — A later head published to the reused pull request reads its text after the push and updates the supplied title and body, recording `requested`, `before` and `after` digests; Pod's own update is the next baseline. Only supplied fields are written, text equal after line-ending normalization writes nothing while a whitespace-only edit such as an indented code block conflicts, and a publication with no supplied text issues only the push and lookup as before.
- <a id="a1079"></a>**A1079** — A person-edited pull request is not overwritten: the row records `conflict`, `decision: lead`, the edited fields and `before`, the outcome stays PASS, and the next head conflicts again. Text Pod never recorded counts as edited. `replace_edited` naming text that has since changed conflicts again, and naming exactly the current text replaces it, recording the `replaced` fields.
- <a id="a1080"></a>**A1080** — An unreadable pull request, one whose base changed, or provider text that is not valid Unicode is not written (`unread`); a lost edit, or one whose answer exceeds the output bound, is `uncertain`, and the next publication treats exactly both texts as Pod's own, so an older Pod text a person restores afterwards conflicts; an edit refused before submission is `failed`; a revoked standing authorization, a withdrawn vouch of a decision-bound grant or a candidate prepared after the push holds the edit (`held`) without consuming a relay receipt, which a grant still valid also leaves unchanged; a `TypeError`, `RuntimeError` or `AttributeError` in the text step records `unread` and keeps the derived validation; every such row stays PASS with its publication facts.
- <a id="a1081"></a>**A1081** — A malformed `replace_edited`, one on another kind, a title or body with a lone surrogate, or another `pull_request` key refuses `invalid_pull_request` before any record or remote call; the port issues only the exact text read and edit argv, and the allowlist refuses other edit shapes. Installed Governor guidance explains the conflict and the lead's decision.

### R244 — Refuse a delivery on a mapless checkpoint by name

Type: B · Scenarios: [A1093](#a1093), [A1094](#a1094)

A checkpoint carrying `delivery` while the objective has no stored obligation map refuses `delivery_unverified` with detail `map_missing` and the next action "record the delivery in a checkpoint that carries the obligation map", whether or not it carries `seq` or any other map field, and writes nothing: like a closing write, it defers a proven runtime-continuity rebind, so the refusal persists none. Pod refuses rather than records because an R93 or R209 delivery is verified against the bound map's sequence, governance and obligations, which a mapless write does not have. A request shape refusal from R209 keeps its precedence. A mapless checkpoint without `delivery` keeps its existing behaviour.

- <a id="a1093"></a>**A1093** — With no stored map, a checkpoint carrying an R93 `{record}` or R209 `{local_append}` delivery and no map field, on the first write or after an accepted mapless write, including after a proven runtime change through the real authority join, refuses `delivery_unverified` `map_missing` with the next action naming the obligation map, and the objective's files and record are unchanged.
- <a id="a1094"></a>**A1094** — A mapless checkpoint without `delivery` is accepted as before, stores no delivery or obligations, and a later mapless write replaces its core.

### R252 — Settle a validation row GitHub no longer retains, from Pod's own reads

Type: B,H · Scenarios: [A1125](#a1125), [A1126](#a1126), [A1127](#a1127), [A1128](#a1128)

`governor-outcome` with `outcome: UNKNOWN` and `settlement: provider_unretained` records that GitHub retains no run for one validation row: an allowed `workflow_dispatch` or `validation_rerun` with purpose `validation`, pending or UNKNOWN, carried or performed. "Not retained" covers a run that was deleted, one that expired and one that was never created; the reads cannot tell these apart, and the settlement never claims that a run once existed. Pod makes the reads itself, with no provider receipt or detail from the caller, and records nothing when a read gives no exact answer. Exact reads must first show that GitHub holds the row's workflow file and its commit (HTTP 200 naming exactly that file or commit), so a listing on them is meaningful. Every row then needs a complete, empty list of the workflow's runs on that commit, of any event at any time, and a row holding a run id (its stored run, or the failed run a rerun reruns) also needs GitHub's exact 404 for that id. A stored id is never taken as proof that it was the row's own run, whatever event it records, because an earlier Pod recorded events without R115's commit and workflow checks; its 404 shows only that one run gone. An empty list alone never suffices, and a list with a member that is not a run is no answer. A call that may still be in flight is not read as absent before its absence floor. Any listed or retained run refuses with `governor-reconcile` as the next action; a merge, push, pull-request update, diagnostic, cancellation, release or deploy row refuses before any read. The row stays UNKNOWN and keeps every earlier receipt field; it gains `unretained`, which records the settlement, its time, the workflow, the commit, the bound run if any, each exact read with its status, the list's scope, limit, count and truncation, and the statement that nothing is compensated. A repeated request answers from that record. A later readback that finds the row's run still settles it as before.

An objective that claims no delivery may close with such rows, the way R144 preserves superseded validations. The closing write applies only when every unsettled row is an UNKNOWN validation row with this settlement, finalization names only validation readbacks and closure, and neither the objective nor any predecessor its succession chain continues records a delivery or a merge PASS; a chain or journal that cannot be read keeps today's rule. It repeats Pod's reads at that write: a row they still prove is recorded under `closure.preserved` with reason `provider_unretained`, its kind, workflow and commit, and the journal stays byte-identical; a row they no longer prove, or cannot read, holds the closure and is named. A predecessor journal is read through the Governor's no-follow record read: a missing journal is empty, while a link, a dangling link or an unreadable file keeps today's rule. A delivered objective, and every other unsettled row, keeps today's rules. Nothing else about Governor outcomes or closure changes.

- <a id="a1125"></a>**A1125** — A claim-only successor of an undelivered predecessor carries a publication-derived validation whose run is not listed; its closing write is refused as before. `provider_unretained` then records UNKNOWN with present workflow and commit reads, an empty, untruncated listing at limit 20 and the not-retained statement, and a repeat answers from the record without a write. The closing write then closes, names the row under `closure.preserved` with reason `provider_unretained`, leaves the journal byte-identical and makes no remote mutation; status shows the preserved row.
- <a id="a1126"></a>**A1126** — `provider_unretained` on a merge, push, pull-request update, diagnostic, cancellation or non-validation dispatch row refuses `outcome_evidence_required` / `not_validation` with no read and no write, and an outcome other than UNKNOWN, a provider receipt, a detail or another settlement name refuses `invalid_outcome`.
- <a id="a1127"></a>**A1127** — A run still listed on the commit (of any event or time), a bound run GitHub still holds, a workflow or commit GitHub answers 404 for, and a row whose call may still be in flight refuse `unretained_unproved`; a read without an exact answer, including a run list with a member that is not a run, refuses `readback_unavailable`; each writes nothing. A row holding a stored run id, with or without a recorded event, is refused while any run is listed on the commit, and settles with the empty list and that id's 404 recorded. The port reads only the three exact `gh api --include` paths and counts only an exact 200 naming the same identity or a 404 Not Found.
- <a id="a1128"></a>**A1128** — A settled objective whose closing read lists a run again is refused naming the held row with nothing written; with a predecessor journal replaced by a dangling link, or a merge PASS recorded by its predecessor, the closure keeps today's refusal, preserves nothing and writes nothing. A stored closure accepts only the exact unretained preserved shape (UNKNOWN, reason `provider_unretained`, a full commit) alongside the existing superseded shape.

### R94 — Objective cleanup plan and consent

Type: B,H · Scenarios: [A170](#a170), [A171](#a171), [A172](#a172), [A410](interface.md#a410), [A476](#a476), [A477](#a477), [A485](#a485), [A498](#a498), [A499](#a499), [A500](#a500), [A976](#a976), [A977](#a977)

`internal cleanup-plan` is read-only and objective-scoped. It describes guarded commands and current facts, never executes cleanup or records a native lifecycle event. Ordinary cleanup keeps its scoped batched confirmation, including an existing exact-scope instruction; unique work is retained or preserved by a verified branch bundle before ref deletion unless separately confirmed for discard. Native settlement and Delivery acknowledgment follow Orca, and release remains an explicit coordinator Orca step under R124.

A completed operation's leftover `AUTO_MERGE` is a recovery root like `ORIG_HEAD`: its object identity is recorded and checked against the surviving closure, so it holds only when its tree is otherwise lost. A real operation in progress (`MERGE_HEAD` and the other merge files, rebase directories or `REBASE_HEAD`, the sequencer, `CHERRY_PICK_HEAD`, `REVERT_HEAD` or bisect state) still protects the worktree, and the reason names it. A resource the objective recorded that no longer exists reads `absent`, with no argv, no protection reason and an `identity.current` of `status: absent`, and is neither covered nor asked about: a worktree that Git no longer registers, whose path is positively missing and that Orca no longer lists (Orca still listing it holds and says so), a local branch whose ref is stably absent from files storage with no checkout, or a remote branch the remote answers without. A failed or uncertain read is never absence, and each absence is read again at the end of the observation (a worktree's path also after Orca's answer): a resource that came back, also during a selected observation's own reads, refuses `cleanup_changed`. Classification of existing resources is unchanged.

A genuinely coordinator-closed objective with ALL current mapped PoDs proven complete makes its exact task leftovers disposable without a Git bundle or file archive, including unmerged commits and uncommitted files. This default needs no further confirmation merely for that completed-task condition. It does not change UNIQUE facts, claim integration or widen a standing yolo decision. Its applicable instruction appears through the existing `standing_authorization.covers` and `asks`: actionable nonprotected rows need no question under this default, while independent holds remain holds.

Completion composes supported current records: validated coordinator closure, a current quiet public status with complete native settlement, and a nonempty complete set of current mapped/proven PoD lines checked against the actual live bound source. Every line must occur once, be ticked, have current satisfied proof, and have no ambiguity, blocked/due status or closure limitation. Empty/missing ticks, checkboxes alone, retirement, continuation, evidence closure, remaining-gate lists or absence never establish this condition. A changed/unavailable source or status holds the default. The existing opaque Git diagnostic and whole-row expect bind the actual completion/source facts; they are rechecked in the same observation. No new proof endpoint, certificate, registry or authority flag is introduced.

The default retains live-process, attached-terminal, open-reservation, Director/lead/role, canonical/default/target/shared, exact current path/ref/identity, OID, lease and uncertain-effect protections. Pod observes only its supported current resource association: checkpoint worktree/branch, exact admission placement and actual Governor publications. A missing worktree's `branch: null` proves no remaining-ref ownership. The executor must retain its existing original finite scope and current association checks; new expect or current absence never proves an earlier removal, release or transfer. ### R115 — Exact provider run binding

Type: B,H · Scenarios: [A285](#a285), [A286](#a286), [A287](#a287), [A288](#a288), [A289](#a289), [A290](#a290), [A291](#a291), [A948](#a948), [A949](#a949), [A950](#a950)

A Governor workflow row binds only a run its own effect could have started: one of its events, its exact head commit, created at or after its submission, and its own attempt. A publication-derived validation row, internally kind `workflow_dispatch` with `derived_from`, binds only a `push`, `pull_request` or `pull_request_target` run: a branch publication starts push runs and, on a branch with an open pull request, pull-request runs, and Pod cannot tell whether one was open. A run of another event, such as `workflow_dispatch`, `schedule` or `merge_group`, is never proof for that row. Requested dispatches and remote diagnostics bind only `workflow_dispatch` runs. These rows bind the run's first attempt. A validation rerun binds only the attempt provider facts prove its own. Before submitting, Pod durably records with the row the run, the latest attempt read just before and the submission start, and keeps them through every interruption and error; a rerun whose run cannot be read reruns nothing. Right after GitHub accepts the call, the row records that acceptance. One rule attributes a rerun's attempt on every path that reads one: execution's immediate read, readback, a reservation's outcome readback, a merge PASS's readback of its unit's effects and a carried row's readback. Attribution is proved by the count: Pod's accepted call creates an attempt, so when the row records that provenance (the submission start at full precision) and the acceptance, and the run shows exactly one attempt after the pre-read, that attempt is Pod's and no other actor's can be it. The attempt's start (GitHub's per-attempt `startedAt`) is only a contradiction guard, at the provider's precision: GitHub sets a rerun's start at the request in whole seconds, so the attempt binds when its start is not in a whole second earlier than the second containing the recorded submission start. Pod floors its own timestamp to that second only to match the provider's precision, never further. Every other state holds the row pending or UNKNOWN with a reason naming it: no recorded provenance, including an attempt an earlier Pod bound to a pending row without it, a caller-performed rerun reservation and any row recorded before this rule; no recorded acceptance (an interruption inside the call, or a lost reply), since a single new attempt may then be another actor's while Pod's own never landed; two or more new attempts; a start in a whole second earlier than the submission's, which contradicts the record whether another actor started the attempt or this host's clock and GitHub's disagree, or no reported start; and a recorded acceptance while the run still shows no new attempt, a contradiction that records no outcome. Only an unconfirmed rerun, with the exact run view showing no attempt after the pre-read once the call's time limit (120 s) and the 600 s absence margin have passed, reads FAILED with that reason, never no-effect. Pod's own earlier rows are never taken as the run's complete history. A held rerun is never resubmitted. Limitation: GitHub reports no requester per attempt and only whole-second starts, so a held rerun, including Pod's own attempt that appears in an earlier second through host clock skew, stays unsettled and blocks ordinary coordinator closure; R145 evidence closure preserves an unattributable result as UNKNOWN when delivery is proved, with no owner decision. Pod records the proved attempt with its event and reads that attempt by number afterwards, under the same rule; a later attempt, whoever started it, never settles the row. A run already bound to an unsettled row, whoever bound it, is verified exactly as a newly selected one: its event, head commit, creation at or after the submission and first attempt, and its exact workflow by appearing in the list GitHub filters by workflow file and commit, since a run view names only a display name. One that fails is kept as `rejected_run` (naming `head_sha` for a commit mismatch, or a `reason`) and never binds; one that cannot be verified holds; settled rows read as recorded. `gh run list --workflow --commit` filters on GitHub; each lookup states its scope, its limit of 20 runs, whether the list was truncated (the port asks for one run more) and that GitHub lists only the runs it retains. Missing or partial history leaves the row pending, or UNKNOWN, with that reason kept as its `readback` note: never FAILED and never proof of no effect. A truncated list settles and binds nothing, on every path, right after the list is read: readback, a bound run's verification even when that run is visible in the list, a landed publication's binding of its runs, execution's run lookup, a reservation's outcome readback and a merge PASS's readback of its unit's effects. An earlier Pod (0.12.0) loads these rows unchanged and ignores `readback`, `attempt` and `head_sha`; if it reconciles such a row it applies its own looser matching.

A publication that moved no remote ref started no run, so its derived row may bind an earlier one, never one created before the remote's newest update of the branch to the head. Pod records a push's `ref_changed` from Git's porcelain (`=` is up to date, so false). A push that moved the ref keeps its submission as the floor and reads no activity. A `remote_update` floor Pod's own readback recorded on the row is reused before anything else, since that history never changes: neither a later list that no longer shows the update nor a successor whose journal lacks the publication rejects the run bound from it. Otherwise a push that did not move the ref, or a row without that fact (an older or hand-recorded one), reads the branch's GitHub repository activity (`gh api repos/{owner}/{repo}/activity?ref=refs/heads/BRANCH&direction=desc&per_page=21`, limit 20, one more asked to detect truncation). This host's clock may lag GitHub's, so once readable activity shows the head being set, the floor is never below the newest update that set it. Pod takes N, the newest of the 20 listed updates that set the branch to the row's exact commit and is not a deletion, over the whole listed history, before or after the submission: GitHub's times may lead the host's clock and the branch may move while the push is in flight, so N is never older than the update the no-op push found. (1) When N's whole second is complete and agrees, the floor is N's second, basis `remote_update`. (2) When N's second is ambiguous (another update listed in it, or the update past the limit in it, names another commit or is a deletion) or incomplete (the list was truncated and the update past the limit shares that second, so it may go on past the response), the floor is the start of the next whole second, basis `remote_update`, with a note naming the ambiguous second; the submission is never the floor in these cases. (3) Rules 1 and 2 apply to every row whose facts are not `ref_changed: true`, older rows without the fact included: where N is in or after the submission's second its floor is at least that second, so it is never weaker than keeping the submission. (4) Readable, non-empty activity in which no listed update sets the head (another commit, a deletion, another ref, or a truncated list without one) gives no floor: the row holds with a note, nothing binds, and a bound run is neither accepted nor rejected; the next readback may settle it. (5) Without activity information (an unreadable read, an unsupported shape, an empty list, updates not listed newest first, an update without a readable time, the one past the limit included, or no recorded publication facts) the submission stays, basis `publication`, with a note saying why. (6) At execution, a push whose porcelain says it moved no ref binds no triggered run, since it started none; its derived row, like any row derived from a publication whose facts say it moved no ref, binds only by readback under its floor. Both readback paths, a bound run's verification and a new selection, use the same floor, and a held floor holds both. When Pod derives the row it records the publication's facts on it as `publication` (the branch pushed and, when known, `ref_changed`); a carried copy's marker keeps them as readback facts, unchanged on every later hop, and for a row derived before the field takes them from the predecessor's publication row at the claim, so the floor is the same where the settled publication row is absent. A carried row without them keeps the submission and says so. These facts come only from Pod's own records, never from caller input, and the carried-row and R116 restrictions are unchanged (no manual PASS, no provider receipt by hand). The run must still be a `push`, `pull_request` or `pull_request_target` run on the exact head and its first attempt; a run created before the floor never binds. Every path that applies the floor (a bound run's verification and run selection) states the time used and whether it is the submission or the remote's newest update of the branch to the head, with the floor's note (why the submission stays, which second was ambiguous, or why the row holds without a floor) kept in the hold's `readback` note; a settled row's provider records `created_after: {at, basis}` with basis `publication` or `remote_update`. A derived row already recorded UNKNOWN settles by `governor-reconcile` readback once such a run qualifies, and nothing else about UNKNOWN rows changes. Requested dispatches, reruns, diagnostics and cancellations keep their rules exactly. The `candidate_unpublished` deferral and the Governor guidance name `governor-execute` publication, never plain git, as the route, since a push Pod did not perform is not one it counts. Limitation: GitHub reports updates in whole seconds, so a floor from an update within the submission's own second equals that second, and a branch moved away and back within one second floors at the next one, so a run created in that second holds. A newest update made after the no-op push (the branch moved away and back later) makes the floor stricter than the update the push found, so a run that qualified may hold; it never binds a run from before the head was last set. Without activity information (rule 5) the submission cannot see a host clock that lags GitHub's, so a run created after the submission but before the update the push found may bind. A floor is only as recent as the updates GitHub lists when it is read: an update not listed yet cannot raise it, and a recorded floor is reused.

### R116 — Each outcome needs its own evidence

Type: H · Scenarios: [A292](#a292), [A293](#a293), [A294](#a294), [A295](#a295), [A296](#a296), [A297](#a297)

`governor-outcome` records only an outcome its evidence supports; otherwise it refuses `outcome_evidence_required` with a subcode and writes nothing. A row Pod performed (an executable kind without the decision-reservation marker, a publication-derived validation, or an unmarked older row) takes PASS, FAILED or CANCELED only from execution or `governor-reconcile`; by hand it records only UNKNOWN, without a provider receipt. A rerun Pod performs records its provenance before its effect and its acceptance right after (R115), so an interrupted rerun resumes by readback and is never resubmitted. Its own attempt is proved by the count, the single attempt after the pre-read once the acceptance is recorded, and its whole-second start is checked only for a contradiction at GitHub's precision; when R115's one attribution rule cannot prove its own attempt, including for a pending row an earlier Pod bound without that provenance, the row stays pending or UNKNOWN and blocks ordinary coordinator closure; R145 evidence closure preserves it without an owner decision when delivery is proved. A merge PASS keeps the caller's provider `merge_commit` and passes R93's Git checks at outcome time; the merge decision and each refusal say to fetch the target first. A merge FAILED or CANCELED needs the fetched target to lack the candidate's result: neither the candidate commit nor, within a bounded walk from the bound base, a commit with its tree. A release or deploy, performed by the project, takes PASS or FAILED only with a provider receipt or an evidence reference. A decision reservation's PASS or FAILED is what Pod's own provider readback shows; the caller adds evidence references only. CANCELED needs a `detail` attesting that the action never ran. For a reservation it also needs the row pending with no recorded sign of execution (a provider receipt, a bound or rejected run, a validation it started) and a readback from complete history that shows no effect; one predicate decides this and whether a helper offers "cancel, then execute". UNKNOWN never becomes CANCELED. An identical restatement answers from the record without a write, and another receipt for a recorded outcome refuses. Existing rows read exactly as recorded.

### R144 — Closure is part of delivery

Type: B,H · Scenarios: [A456](#a456), [A457](#a457), [A471](#a471)

As soon as the source's PoDs are all ticked, delivery is merged and installed where in scope, and the final report is consumed, the coordinator records closure in the same turn, before it may end, be released or have its tab closed. R117 supplies recording order and the ordinary closing checks; closure needs no additional owner decision. A verified delivery's closing checkpoint keeps the trusted governance baseline under R147, adopts no changed policy and records that it did not adopt even when the target moved past that delivery: the closing write's answer carries `governance_adoption` and the stored governance base stays at the trusted baseline.

A delivered objective's closing write is not held by a publication-derived validation row (kind `workflow_dispatch` with `derived_from` a publication, carried rows included) whose commit is an earlier head of a delivery pull request that merged with a different head. The closing write proves the delivery as R145 does (source and every delivery pull request over the chain, read at that write) and reads the pull request's commits. It reads the row back read-only first: a row that would settle refuses the closure with `governor-reconcile` as next action. Otherwise the closure records it under `closure.preserved` with outcome UNKNOWN and reason `superseded_by_merged_head`, naming the pull request and merged head, and the journal stays byte-identical. Nothing is stamped. A zero-run listing alone never suffices. These keep today's refusal until the existing reconcile or accounting settles them: a derived validation of the merged head, every requested dispatch, rerun, diagnostic, cancellation, push and pull-request update, merge, release and deploy rows, a row whose supersession cannot be read, an unconsumed report, and an unproved or unverified delivery. The refusal names the proof's conditions and each held row. Status stays record-only (R114). Readiness names the coordinator next with a summary starting `Delivered, not closed:` while only such derived validation rows and closure remain. [R252](#r252--settle-a-validation-row-github-no-longer-retains-from-pods-own-reads) separately lets an objective that claims no delivery close with validation rows settled `provider_unretained`.

### R136 — Record a standing authorization ("yolo") for one objective

Type: H · Scenarios: [A429](#a429), [A430](#a430), [A433](#a433), [A434](#a434), [A435](#a435), [A436](#a436), [A438](#a438), [A441](#a441)

The owner may put one objective in yolo mode by recording a standing authorization, an owner decision of its own kind that the Governor applies to each exact candidate as it comes (R137). While it is active, the coordinator does not wait for the owner at the effects it covers. It removes only the wait for consent: it is not blanket permission, and no Pod gate changes.

The objective context holds one append-only `standing_authorization` record, `pod-standing-authorization/v1`, retaining decisions and responder answers without lifetime quotas under R180. Each complete stored decision, including its verifier verdict, remains limited to 4096 encoded bytes; each answer to 8192 bytes. Shared text limits still apply, including 1024 characters for `instruction`. Oversized individual rows refuse before consuming authority or writing state. Closure uses compact decision references rather than copying verifier verdicts. Status bounds its display with explicit totals/truncation; immutable storage growth does not truncate retained authority, change expiry, grant scope or make a stale decision current.

A decision uses R120's shared validator (`provenance: user_direct`, `instruction`, optional `channel`, and `relay` exactly when relayed) and adds a Pod-assigned `id` (`Y1`, `Y2`, ... in order), an `operation` (`activate` or `revoke`), `utc` from Pod's own clock, never from the caller, and the map `seq` current when it was recorded. A session decision's decision time is Pod's clock when recorded. A relay uses its verified `decided_at`, distinct from Pod's receipt time (`utc`). An otherwise authentic, fully verified and exactly bound future-dated activation refuses `standing_authorization_future` without changing objective context or journal or creating an authority row. Its key is permanently marked refused in the existing relay receipt store; every later use refuses `relay_authorization_reused`, even after a stop and after Pod's clock passes `decided_at`. This narrow receipt write never overwrites an accepted, interrupted or refused receipt; forged, mismatched, unverified and malformed inputs write no receipt. A fresh owner decision with a new key remains possible. A future activation is never clamped into a grant. A verified future-dated revoke uses receipt time as a conservative stop barrier and can only reduce authority. Its row retains the original verified `decided_at` and `utc`; status history's `decided_at` is the capped ordering time. The full verdict is preserved. Recording order never substitutes for decision time.

The record also holds `observed`, Pod's latest matching read of the bound source (below), the required `observed_scope_digest`, optional latest `closed_at` and `reopened_at` facts atomically stored with their checkpoint, and one required monotonic authority barrier, `not_before`. That barrier rises to the decision or event time of every recorded activation or revocation, every received stop even while yolo is off, and every closure and reopen of a record holder. While the record exists, `observed_scope_digest` holds one observed material identity, decided at each record write against the checkpoint being written: the material scope digest when Pod's latest read (`observed`) is of the current bound source, and otherwise an unread identity of that bound source (its source digest with the criteria), because Pod cannot attest a body it has not read. Every change of that identity raises the barrier to the write time, so an unread changed source is itself a transition and fails closed. Learning the body of that same, previously unread bound source is not a transition, and Pod's own confirmed tick (R131) carries the observation to its rebound source because it flips one checkbox. This includes a record created by a stop while off, with no activation. Repeating an identical observation does not move the barrier. Every relayed activation independently uses the exact digest binding below. A mismatch with the latest activation also records its bounded id in `scope_changed_for`, keeping suspension sticky through restoration: restoration is not owner confirmation, and an older matching relay stays stale after any intervening observed change. A new activation clears the marker. When a change is first observed during a relayed activation's own live read and that relay confirms exactly the newly observed digest, that observation does not make the relay stale; it records the digest without raising a later barrier. Prior recorded barriers still apply and are never erased by that read.

There is one content-identity limit, only for an objective that genuinely never held a standing record: preserving its 0.18.0 shape leaves no usable history of an intermediate material revision. A verified first activation naming exactly the restored content the owner confirmed may be accepted after A/B/A, under the remaining ordering rules. When that first verified relayed activation creates the genuinely never-existing record, the record also starts at its receipt: the barrier rises once to that receipt time, a distinct admission fact (the row keeps its verified `decided_at`). Other relayed activations decided before the record existed then refuse `standing_authorization_stale` and need a fresh owner decision, the conservative cost of this limit. Later decisions keep owner decision-time ordering, and a stop still compares with the activation's actual decision time and wins ties. The host must have saved that digest with the actual owner decision; it cannot echo a later request or substitute another scope. This proves content identity, not absence of intermediate revisions. It never covers a stop-created record without an activation, known prior standing history, invalid or lost records, or an untimed earlier reopen. Missing or malformed history refuses; recover the existing record rather than claiming the never-record exception. When a new confirmation is needed, obtain a fresh owner decision for the current digest or use an actual coordinator-session activation; the path with an unavailable reopen time still requires that session activation. Stop, closure, expiry, refused-key and host protections remain independent. These bounded facts survive the eight-row reopen history and add no second journal. Closure and reopen without the record create no standing record or new channel discriminator. An activation also records:

- `scope`: a nonempty set of `publish`, `merge`, `release`, `install` and `cleanup`; all five when omitted. `deploy` is in scope only through a widening.
- `widening`: the exclusions the owner explicitly removed, by name; none by default. Naming `deploy` also adds it to `scope`, as in "yolo including deploy".
- `exclusions`, computed by Pod: `deploy`, `paid_resources`, `secrets`, `unique_deletion` and `scope_growth`, minus the widening. Each keeps its normal owner question: production deployment, new paid or cloud resources, secrets, deleting unique or unmerged material outside R94's completed-task default, and work beyond the objective's scope. Pod enforces only `deploy` (outside the scope), a merge that names no pull request and unique material in cleanup mechanically (R137). It records and shows the other exclusions, and the coordinator keeps asking the owner about them.
- `expires_at`, optional: a zoned timestamp later than now, stored in UTC.
- `binding`, computed by Pod: a digest of the objective's scope, which detects a material change (below). It covers the bound issue's repository, number, locator and amendments, the issue body with every task-list checkbox marker (`[x]` or `[X]` at the start of a list item) normalized to `[ ]`, and the criteria. A direct objective's binding covers its criteria only.

The owner turns it on at any time:

- At start, the owner types `/pod <link> yolo`. The coordinator records the activation right after intake and before any admission.
- Later, the owner types a plain instruction in the coordinator's own session, such as "use yolo from now on". The coordinator turns it into the exact decision (scope, widening, expiry) and records it with `channel: session`. Text an executor, a host agent or a mailbox relayed is `relayed`, never session (R120).
- A relayed activation is accepted only when the host verifier's `standing` action confirms exactly this objective, operation, scope, widening, expiry and material `scope_digest` (R139). The request carries `standing.scope_digest`, computed after the activation's own live issue read, equal to the digest Pod would bind now. The host must compare it with the digest saved with that exact owner decision; echoing the request is not verification. A different, missing or unknown decision-time digest refuses `relay_verifier_mismatch` naming `standing.scope_digest`, before key use or a write, with a next action to obtain a fresh owner decision for the current digest. This includes release and, only with an explicit owner widening, deploy; it authorizes no deploy target by itself (R120). Pod stores the complete verdict, takes `relay.owner_source` from it and consumes its `single_use` key for one row. Without a configured verifier it refuses `relay_verifier_unconfigured`; other verifier failures reuse the existing relay codes. A verified relayed widening may name any default exclusion: `deploy`, `paid_resources`, `secrets`, `unique_deletion` and `scope_growth`, each explicitly, under the same exact binding. It never confirms protected credential changes, authorizes host maintenance confirmations, bypasses secret handlers or disables gates. Widening never bypasses the scope binding or suspension.
- An activation of an issue-bound objective reads the bound issue live through the existing issue recheck. A live body that differs from the bound digest, an unreconciled edit, refuses `issue_reconciliation_required` without a write; reconcile first.
- An activation made while one is active replaces it, which is how a later widening or narrowing is recorded. One made while suspended is the owner's re-confirmation.
- Activating restarts and reopens nothing. A consent wait that deferred `authorization_missing` is satisfied at the Governor's next check.

"Stop yolo", typed in the session or verified-relayed, always raises the barrier. It ends yolo unless its decision time is strictly earlier than the latest recorded activation's decision time; a tie keeps the stop. On an active verification path, a stale stop refuses `standing_authorization_stale`, records no decision row and leaves the state. A revocation row is accepted whenever the state is `active`, `suspended` or `expired`. While off, a stop reports the current state without a decision row or key consumption, but persists its barrier, creating the record if needed. A no-op relayed stop verifies its `decided_at`; if verification is unconfigured or fails, the barrier uses Pod's receipt time as a fail-safe. When verification fails while yolo is on, Pod preserves the honest verifier refusal and current state, but raises `not_before` to receipt time, with no decision row or unverified key consumption. A genuinely newer verified decision can still follow. Recorded-key reuse refusals remain unchanged. Objective closure ends an activation permanently; reopening keeps it ended until a new owner activation.

A verified relayed activation must not be future-dated and is accepted only when its decision time is strictly later than `not_before`; otherwise it refuses `standing_authorization_stale` before consuming its key or writing anything. Its verified material digest must also match the current digest, even before any activation, after a second scope change, or after a stop while off. The receipt-only interrupted-write completion obeys the same predicate. Stale and future refusals precede the history-cap check. A session activation is recorded now, after the barrier. A genuinely newer relay remains acceptable when an older relay was recorded late. An objective reopened before it first held the record has no trusted reopen time: genuine 0.18.0 rows kept none. A relayed activation then refuses `standing_authorization_stale` with reason `reopen_time_unavailable` and the next action to activate in the coordinator's session; after that activation, newer relays work. This preserves never-yolo readability without inventing earlier times. Ordering assumes the verifier's clock and Pod's clock agree; a slow verifier clock can still misorder decisions.

The record retains every decision; activation and revocation are governed by their current authority and individual row bounds. R180 provides growth without a lifetime slot reserve or evidence eviction.

One function of the record and the objective context gives the state, used by every reader; the mode is `yolo` only in the state `active`:

- `none`: no decision. `revoked`: the latest decision is a revocation.
- `ended`: the objective is closed, continued by a successor claim or under historical retirement (R112), or its latest standing decision predates a recorded reopen.
- `expired`: the latest activation's `expires_at` has passed.
- `suspended`: Pod cannot show that the objective's scope is the one the owner confirmed. Reason `scope_changed`: Pod's latest observation of the bound issue body, with the current amendments and criteria, gives a digest different from the activation's `binding`. Reason `scope_unobserved`: the objective's current bound source is one Pod has not observed (the source digest differs from `observed`), so a stale binding is never hidden. Any change of body text other than checkbox markers, of the amendments or of the criteria is material, and Pod cannot judge wording, so every such change counts. Checkbox-only edits, including a tick Pod itself wrote (R131), are not scope, and a metadata-only issue edit changes no digest. A material change ends only when the owner activates again; `scope_unobserved` also ends when a later Pod read shows the scope unchanged.
- `active`: otherwise.

Whenever Pod itself reads the bound issue body for the objective's current source and it matches the bound digest, which happens at an activation, at a reconciling or introducing checkpoint and at a tick's readback and rebind, an objective that holds the record stores `observed`: the current source digest and the body scope digest. Its `observed_scope_digest` tracks the observed material identity across those observations and context writes, including criteria changes in a direct objective; a read records only `observed`, and the transition is decided at the following record write. An objective without the record gains no field. Explicit standing `show` reads a short locked snapshot, releases the lock for its bounded live issue read and digest calculation, and rechecks the snapshot under the lock. A concurrent context change returns an unknown digest and a retry action (R139); show stores no observation and never moves a barrier.

Yolo belongs to one objective. A successor claim, a continuation or another objective never inherits it, and the record is not copied; the owner turns it on there if wanted. Runtime continuity and owner handoff of the same objective keep it. A carried Governor row (R118) authorizes nothing new. A host stop halts work as before. ### R203 — Rebind proof across a governance change only by an attested delta

Pod still refuses, `rebind_refused` with the row and reason, where it can see an effect: a change to Pod's own policy source `.pod/config.yaml` (authority changes); a row whose own proof scope names a changed governance path, meaning its declared `proof_scope` or boundary/scope paths, where a scope that merely contains the repository root does not count and a committed symlink in any component names what it resolves to in the bound base, target and candidate Git trees (at most eight hops, within the repository; only regular files, trees and followed symlinks are resolvable, so a path through a gitlink or any other mode, or an absolute, escaping, looping or longer link, refuses conservatively; host paths, submodule checkouts and remotes are never read); and a receipt stamped under governance that Pod cannot resolve. A row whose definition changed, with an open required correction, an ordering fault or a non-governance binding fault stays invalid under the existing checks. Files a worker or reviewer was only given as bound context (a review's sources such as `AGENTS.md`) do not count as proof scope: governance context is exactly what the attestation judges, and `binding_current` already refuses that review as a binding change once the candidate takes the changed file.

A receipt stamped under the bound governance crosses the change from the bound base. One stamped under an earlier governance step, for example a row restated unsatisfied through an earlier refresh and satisfied again from its old receipt, is resolved read only against the bases this record's own governance history names (at most 64): its cumulative change from that base is part of the attestation. When no named base matches, Pod cannot read the change and refuses; that row needs fresh evidence. A rebind across no changed source needs no attestation, as before.

The accepted refresh records `rebind: {rows, delta, reason, bound_context?, earlier?}` on its governance snapshot decision, beside the decision's `seq`, authority and channel: `bound_context` lists rebound rows that read a changed source as context, and `earlier` lists rows that crossed more than one governance step. Status `owner_decisions` and the closure report's `governance_decisions` carry it, and status text prints one line per rebind with each source's added and removed lines. No new command, review, fresh evidence or owner decision is involved. A refresh's `evidence_invalidated` refusal for a governance change lists every rebindable row (bounded by length, with `eligible_rebind_remaining`), the exact change to declare in `governance_delta` and the route; for other rows it names why they cannot be rebound. When the rebindable rows cross no changed source, that route and each row's correction omit `governance_delta` and say no attestation is needed, and a `governance_delta` whose `sources` is empty, refused as malformed, says to omit the key when Pod reads no change.

Why stale proof cannot be promoted: only the governance stamp moves, and only from a stamp whose governance Pod resolves itself; every other evidence predicate is evaluated as before; the change crossed is computed by Pod and must equal what the decider attested; Pod's own policy source and proof about a changed governance file are refused mechanically.

### R209 — Record a host-verified local append as a typed delivery

### R155 — Close the bound source after Pod closure and retry by sweep

An unreadable or unsupported predecessor, or a chain past its bound, retains a chain lead task and authorizes no predecessor effect; a valid ordinary tail still attempts its own source. The helper accepts no caller issue substitution. This effect never writes Pod records, history, report or Governor journal, and its separate `source_issues` and `parents_open` outcomes survive every acknowledgement and sweep adapter.

The closure is validated by replaying the recorded closure (`closed_snapshot_context` for `validate_closed_snapshot`), which accepts exactly what the closing write accepted (pod#117).
