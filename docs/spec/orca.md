Type: H · Scenarios: [A18](coordination.md#a18), [A21](coordination.md#a21), [A22](models/preferences.md#a22), [A59](#a59), [A96](#a96), [A594](#a594), [A596](#a596), [A599](#a599), [A600](#a600), [A611](#a611), [A601](#a601), [A602](#a602), [A603](#a603)

Do not census other objectives or reconstruct physical occupancy. Documented effect-free Orca refusals defer; uncertain errors require exact request and worker readback.

An explicit `abandoned_reason` on the identical original admission selects read-only accounting, never a start or request replay. Its immutable start observations must positively bind the same runtime, Run, Task, Dispatch and request UUID to `outcome_unknown` / `turn_start_unobserved` / `turnStart: unobserved`, the prompt's sole `input_accepted` stage and matching accepted/unobserved terminal effects. A current exact native read must prove failed assignment settlement, worker/stage `abandoned`, `lastFailure: abandoned`, capability revocation and completion timestamps, and the same input and resource identities. Missing or conflicting evidence, an immutable observed start the current readback contradicts, or a known request/retry contradiction refuses. A fence proves abandoned assignment authority; execution remains UNKNOWN, including when accepted input may have run. A current readback that positively shows an observed start (observed turn, start or heartbeat time, a started prompt stage or an observed input effect), on an unresolved start or an already bound admission, selects the same accounting with execution `observed` and the bounded observed facts recorded; an unobserved record never turns observed later and an observed one never regresses. Abandonment is never added to the started-worker states.

The existing admission becomes identity-bound with `abandoned_accounting`, not started or successful. Record the accounting coordinator and reason, immutable request/readback evidence, exact fence and previous error; retain the previous error as the raw native attribution, which stays unidentified. Preserve the original request, route evidence, failures, counters, results and possibly-live resource ownership. Fresh assignment projection rechecks that fence and its unobserved input evidence, and keeps the logical slot until that same read reports the attempt's process exited with no effect beyond the worktree and accepted input left unresolved; a fence, a closed terminal or released-resource bookkeeping proves nothing, and a live, unverifiable, missing or contradictory process verdict always keeps the claim. Orca never releases or reports exited the process of a reused or retained terminal, so for a local attempt with such a terminal, no pending effect and no `exited` verdict, Pod reads the proof itself at every read: the exact terminal handle and incarnation are absent from Orca's complete terminal records, and no same-user process carries that `ORCA_TERMINAL_HANDLE` (a process that vanishes during the scan is gone, a read that fails otherwise is unknown). The proof is Pod's own observation made at that read, never the caller's or an earlier read's (any proof already on the observation is discarded first, and only a proof made by that read is accepted); a terminal record without both a handle and an incarnation makes the inventory incomplete; only an EACCES refusal of a process's environment skips it, and a failed owner lookup or any other error is unknown; it releases the slot with source `terminal_closed`, distinct from Orca's `process_exited`, and is never a success, start, report or "never started". A present terminal, a live or unknown carrier, an incomplete inventory or a pending effect keeps the claim, and a later read where the terminal is present again holds again. The claim is derived from the fresh read for every bound abandoned attempt, whether or not accounting was recorded, so no replacement is admitted and no discard is accepted while it may run, so otherwise the slot stays a hold scoped to the attempt's worktree, branch, paths, surfaces and pending-effect identities, which refuses another assignment in that worktree or branch or that may touch a pending effect's target. Orca's own observations decide which effects are pending: the worktree, the accepted input, a setup that was not applicable, skipped or completed, and a created or reused terminal leave nothing unresolved once the process verdict is known, so a missing identifier on one of them is never a conflict; any other effect, or a list that cannot be read, is pending with its full identity. A `push` names a ref of its own repository, as the Governor's action kinds define it: the same ref name in another repository is independent and an unknown repository on either side is not. Any other pending effect, or one without an identity, is a target no placement can prove independent of and holds every assignment until Orca reports it resolved. The hold counts for every Governor unit, including validation by a review on the exact candidate, while an independent worktree, branch and target stays usable, and releases on a later exit or release read without another accounting or worker. Accounting supplies no worker report, integrated output, terminal reuse or retry-parent eligibility. A settled implementation still requires the ordinary `discarded: true` disposition with a reason before replacement work (nothing in the worktree is deleted; the disposition only declines it as accepted output); a review's reservation of its assurance obligation and its report-consumption record end with the claim, with no report manufactured and the obligation still unsatisfied until replacement proof exists (investigation is a tracked follow-up); Governor's source, integration and effect guards remain unchanged, except that an accounted attempt the exact native read no longer holds is non-material history: it vetoes neither route readiness nor finalization, and is reported separately, while a live or unknown claim stays outstanding and blocks. No stop, release, Task mutation or resource deletion is performed.

### R110 — A successor's claim ends a lost coordinator's authority

Type: H · Scenarios: [A260](#a260), [A261](#a261), [A262](#a262)

R145 evidence closure is the next action for a delivered lost objective; a claim remains an optional authority path requiring its existing user_direct decision. A successor objective may claim its predecessor before it starts work, through `internal succession` from the successor's live recorded coordinator with the successor's Run authority. The claim ends the predecessor's write authority and gives it to no one: its owner, admissions, Runs, map and evidence stay as recorded, and nothing is converted, started, settled or released; only the Governor rows R118 carries are copied into the successor. Without a decision the operation returns fresh facts and a plain question naming both objectives and no handle or Run, and writes nothing. Only a `user_direct` decision with the owner's instruction and exactly `predecessor`, `predecessor_owner`, `successor`, `successor_owner`, `runs`, `ambiguity` and the `carried` rows (R118) from those facts permits the claim; a verified owner continuation instruction may be relayed and recorded with `channel: relayed` and its complete relay under R120. A mailbox message is never itself a decision; the recorded decision conveys the owner's verified instruction, never the coordinator's inference from a message.

It never steals. Orca must report the predecessor's recorded coordinator handle stale or gone, or show it exited: not connected or writable, with a confirmed exit cause (`operator_close`, `signaled` or `exited`), as Orca keeps a deliberately closed terminal's record; an `unknown` cause, such as a stop Orca never confirmed, is not an exit. Each predecessor Run's current coordinator, read by run show, must be absent, that handle, or another handle that is stale, gone or exited. Owner handoff (R105) still requires stale or gone; every Dispatch on its Runs and every bound admission must read settled with its exact recorded identities, from a complete worker list; and it may have no unsettled Governor effect that R118 cannot carry, unfinished owner handoff or unresolved admission. A reserved admission with no Dispatch is a named ambiguity the decision must carry, and the claim records it; one with a Dispatch holds. The successor must be recorded, open and not started: no admission, Governor work, settled obligation, delivery, closure or other continuation. The predecessor must be a readable current record of the same repository, open and unclaimed, not the successor itself, and not itself the successor of an incomplete claim (R118).

Detection never writes the predecessor or completes a link; the successor's own authority join may record an ordinary R98 rebind. Under both objective locks, taken in path order, the successor first records its reservation (R118), then the predecessor records `continued_by` (successor, record, owner, Runs, time, instruction, unfinished obligations, unreported settled admissions, accepted ambiguity and `orca_claim: unavailable`), then the successor's Governor journal receives the carried rows (R118), then the successor records `continues`. An exact replay with a decision writes nothing new and completes a successor link an interrupted claim left out; status reads that successor `claim_incomplete` until then, and a successor that already continues another objective refuses `successor_started`. A second claim refuses `predecessor_claimed`. Afterwards every write of the predecessor, including its own recorded coordinator's checkpoint, admission, report, Governor, runtime-continuity and worker-start paths, and any owner handoff, refuses `objective_continued` naming the successor; status still reads it. Status lists its open admissions as settled by the claim (`settlement: claim`, or `claim_no_dispatch` with its basis and a render line for a named reserved row), never unverified, and shows the claim's accepted ambiguity. Detection of a recorded claim returns that claim's facts, so its own decision completes an interrupted link. The R108 list keeps its phase `continued` and shows `succession_state` `successor_open` until the successor chain (at most eight) ends in an ordinarily closed or evidence-closed objective (R146), then `successor_closed`; that means the successor closed, not that the predecessor's obligations were proven. A predecessor whose earlier successor closed without a claim is continued by a fresh successor that claims it, then closes. A cleanup plan for the predecessor protects every worktree its successors record, and all its worktrees when a successor's location is unrecorded or unreadable, or the chain loops or exceeds eight successors. A native-start evidence file for a start Orca accepted before the claim is still kept beside the record; the record itself is not written. Orca offers no worktree claim or conditional send (R111), so the claim binds none; a prompt Orca already accepted for the old terminal is outside Pod's control. The claim is a cooperative Pod record, not an operating-system fence: it does not stop a process of the old coordinator that is still running.

### R159 — Continue a coordinator a verified owner-authorized Orca window ended

An owner-authorized Orca stop or restart ends every live terminal. `pod continue --objective ID` (internal `window-continuation`) lets a new coordinator continue an open objective whose recorded coordinator such a window ended, with derived provenance and no per-objective owner decision. It is a third coordinator-change path beside R105 and R110; a direct owner decision stays accepted where given, and a host with no configured authorization verifier offers no window route, so its existing paths stay exactly as they were.

The current runtime differs from the recorded one and may be later than the window's own after-runtime, so one window can cover two runtime changes. A drain or hold that ended no session, a restart nobody authorized, a coordinator the host did not see live, an ambiguous, stale, inconsistent or unverifiable answer each refuse with the host's bounded condition or `window_unverified`.

Pod proves the rest from fresh reads. Orca reports the recorded coordinator handle stale or gone; one Orca shows closed at the current runtime ended outside the window. The recorded worktree is still its recorded repository, key, path and branch, and the caller is a live non-worker terminal running there. The Run exists, no other open objective records it, and its holder and generation are the recorded ones or this objective's own pending continuation's; Pod never creates or adopts a Run. Every outstanding admission's identity is compared at the current runtime, and a differing identity refuses. Each is recorded `settled` (terminal Dispatch outcome read), `unknown` (with its reason) or `absent` (a reserved Task with no Dispatch). No admission state, report, outcome or evidence changes; later settlement uses R25, R28 and R45.

Under the objective lock the operation preflights the pending and done record capacity, consumes one relay receipt keyed by window effect, repository key and objective whose transition is fixed by the original owner, Run, generation and runtime, and writes a `window_continuation` pending row. For a fresh or replacing attempt it calls `orchestration run-use --id RUN`, rereads, and writes the row done with the new owner, admission owners and runtimes, reference runtimes and continuity binding. It carries no `user_direct` decision, instruction or channel; the objective's earlier decisions, consent and standing authorization keep their provenance and limits.

A rerun by the same caller finishes an interrupted attempt; a caller whose pending attempt Orca reports lost is replaced; another live claimant is refused; a done replay writes nothing. A retry after an ended attempt and the replacement of a lost claimant are new attempts and refuse `attempts_full` beyond four earlier ones; the pending claimant's own rerun is none. A refused or unknown run-use ends the attempt only on authoritative proof that the Run did not move, and only the caller's own attempt ends, on a definite objective-level loss; a caller in the wrong place never ends one.

`pod status --objective ID` and every non-owner authority refusal show a `window_continuation` block: the objective's eligibility, which includes the attempt bound, a pending attempt, and whether this terminal could run the step. Its next action, the command in the recorded worktree or the precise lead task, comes first, and owner handoff and successor claims stay optional with their own decisions. R108 lists the same eligibility for open rows, with discovery returning within one wall-clock deadline and unfinished or late checks reading `unknown` / `discovery_budget`; there a failed, timed-out or partial read (the Run, the recorded coordinator's handle, the worker list, peer records or the verifier) reads `continuation unknown` with its reason, never a refusal. Every refusal is a task for the project lead, never an owner question. A repository move is out of scope: records are found by the checkout's Git directory. R118 treats a done continuation as authority movement, and recorded runtime lineage follows done rows. Older helpers refuse a record carrying this row as unsupported.

### R145 — Close delivered work by evidence when its coordinator is gone

Type: B,H,I · Scenarios: [A458](#a458), [A459](#a459), [A460](#a460), [A461](#a461), [A462](#a462), [A463](#a463), [A468](#a468), [A474](#a474)

Any caller, including a project lead, executor, successor or host cleanup, may close proved delivered work without an owner decision. `evidence_closure.prove(project, objective, ...)` is one bounded read-only proof returning `{status, conditions, facts}`. Status is `proved`, `not_proved`, `unverified` or `not_applicable`. Conditions list every unmet condition found, each with code and plain message, so the lead has the complete task. Checks run cheapest first (record, Orca, GitHub), continuing after unmet conditions where safe. A `not_proved` condition wins over `unverified`; otherwise any unverified condition prevents proof. R146 defines record and chain scope.

- A current record validates normally; an older record uses R146's documented fields. A needed malformed or unreadable field is `unverified` / `record_unreadable`. An unknown or future schema is `not_applicable` / `schema_unknown` and never closes. Ordinary closure, evidence closure, retirement and continuation are `not_applicable` with `objective_closed`, `objective_retired` or `objective_continued`; the tail of a continuation is the candidate. R118's incomplete, unverified or ambiguous claim predicates remain `unverified` with their own code.
- The recorded coordinator must be gone by R110's loss proof: stale or gone, or exited with confirmed `operator_close`, `signaled` or `exited` cause. No recorded owner gives `not_proved` / `owner_unrecorded`; live gives `not_applicable` / `coordinator_live` and the coordinator closes itself under R144; any other observation gives `unverified` / `owner_unverified`.
- Recorded Runs are checkpoint native_refs plus admission run ids. None gives `not_proved` / `runs_unrecorded`; an unreadable Run, or a Run reply that omits its coordinator field (run_show `coordinator_known: false`), gives `unverified` / `workers_unverified`. Each Run holder meets R146.
- Each Run's worker list must be complete. Every Dispatch on it and every bound admission's Dispatch must be settled with matching recorded identity. A live or unsettled Dispatch, or a reserved/unresolved admission's start request Orca still reads pending, gives `not_proved` / `work_live`; unreadable or differing identity gives `unverified` / `workers_unverified`. These retain R112's work safeguards.
- The Run and work checks above run, read fresh, for every record whose closure entry will be written: the objective and each continued predecessor of R146's chain, each on its own recorded Runs and admissions. A claim ends the original owner's authority over that predecessor only; an open recovery objective that owner later holds on the Run still gives `run_held`. A condition found for a predecessor names it, and holds the whole chain.
- The source is every distinct GitHub issue that a member of R146's delivery chain binds, the objective's own first: a claim-only successor, or any member without its own issue binding, is proved by the issue its claimed chain binds. Read each live issue: at least one R130-recognized PoD line with every line ticked proves `pod_ticks` (including repeated numbers, as delivered by #82), or CLOSED with stateReason COMPLETED proves `issue_completed`. Otherwise `not_proved` / `source_unproved`, naming the issue and the member that binds it; GitHub unavailable gives `unverified` / `source_unreadable`. Only an objective whose chain binds no issue is a direct objective, and only a current record can prove its `recorded_criteria`: every criterion of its own is satisfied or validly withdrawn, at least one is satisfied, and its R93 verified delivery record exists. A claim-only successor without its own delivery uses the direct source of its completed claimed predecessor, with the same criterion proof required of each claim-only successor along that certified succession chain. The source names the predecessor whose criteria and verified delivery prove it; recovery peers supply no direct source. A standalone direct objective still needs its own verified delivery. Every recorded delivery PR across the chain must still be merged.
- Read every recorded delivery PR across R146's chain on GitHub in the record's repository. PRs come from Governor merge action `pr`, any Governor receipt `provider.pr`, and a verified delivery record's PR when named. When none is recorded, R153 may prove linked GitHub delivery; otherwise no PR gives `not_proved` / `delivery_unrecorded`, except that a chain Pod could not read whole claims nothing unrecorded, since its unread member's own condition already holds the proof; OPEN or CLOSED unmerged gives `not_proved` / `pr_not_merged`; unreadable gives `unverified` / `pr_unreadable`. Every PR must read MERGED, retaining number, URL, merged_at, merge commit and recorded_by. More than 16 PRs gives `not_proved` / `scope_too_large`.

For a lost coordinator whose delivery is not proved, status's own `next_safe_action` and `next_action` name the project lead's task with the first unmet condition, say that `pod sweep` closes the objective once the conditions are resolved and that a successor claim or owner handoff stays optional with its own recorded decision, and keep R105's warning against a manual run-use; they never ask the owner. The `owner_handoff` block keeps every R105 fact as that optional route. This revises R114's new-fields-only rule for these two earlier fields only.

Pending or UNKNOWN allowed Governor rows do not block delivery proof. When a row has a unit, use Pod's existing read-only governor_effects._observe readback (R118): a settled answer is preserved as `reconciled`, PASS or FAILED with evidence. Otherwise preserve UNKNOWN and its reason, including no unit, release/deploy without readback, provider unavailable or a hold; FAILED stays FAILED. Reserved/unresolved admissions remain UNKNOWN and bound admissions without validated reports remain `unreported`. An unreadable older journal contributes no PR and preserves one `{kind: journal, outcome: UNKNOWN, sha256}` row. More than 64 preserved rows gives `not_proved` / `scope_too_large`. No result is stamped and no journal is written.

`close_by_evidence(project, objective, *, caller)` takes the objective lock, re-runs proof, and writes only when proved. It exclusively creates `closure-evidence.json` beside the record, using O_EXCL and fsync of file and directory, and answers `closed`, naming in `predecessors` each predecessor entry it wrote (R146). When the closure already exists and every predecessor entry it names exists too, the call returns `replayed` and writes nothing. When an interruption left a predecessor the stored closure names without its entry, the retry first proves each such predecessor's Runs and work fresh, as above. While any condition holds, it writes nothing and answers that proof's status and conditions with the stored closure, a task for the project lead. Otherwise it writes only those missing entries and returns `chain_completed`, naming them in `predecessors`; that replay recovery is the only write an existing closure ever causes. No file is ever rewritten, repaired or deleted. Context, Governor journal and history bytes stay identical. R146 defines chain writes; R147 fences every later write.

The canonical bounded JSON record has schema `pod-evidence-closure/v1` and fields `schema`, `objective`, `repository` (repo key), `at` (UTC), `statement` (`closed by evidence, coordinator gone`), `basis` (`evidence`), `caller`, `pod {version, bundle_digest}`, `record {class: current|older, context_sha256, governor_sha256 or null}`, `coordinator {handle, liveness, cause}`, `runs [{run, generation, holder}]`, `dispatches_settled`, `source {locator, repository, number, proof, state, state_reason, pod_lines {ticked, total}, body_sha256, bound_by}` (the first issue proved, or a direct objective's recorded criteria), `sources` (every issue source proved, each in the same shape; empty for a direct objective), `delivery [{pr, url, merged_at, merge_commit, recorded_by}]`, `chain [{objective, relation, phase}]`, `preserved`, `counts {reconciled, unknown, failed, unreported}`, `unfinished` (nonterminal obligation ids), `worktrees` and `locations_complete`.

Every reader projects an evidence-closed record as `status: observed`, `blocker: objective_closed`, top-level `evidence_closure` (the file plus counts), readiness `closed`, `acts_next: none`, `coordinator_needed: false`, `reason {basis: evidence, closed_at}`, and a summary starting `Closed by evidence, coordinator gone:`. Assignments have no active or unverified rows and preserve results under `preserved`; open admissions read `settlement: evidence`. `retained_terminals` is empty and checkpoint_join.native_refs comes from the record. Listing is R108; cleanup reads it closed under R94.

Only a non-owner status reader whose readiness is `coordinator_lost` computes this proof, using Orca and GitHub reads. Readiness acts next with `lead`; its first recovery route is `evidence_closure`, available for proved, blocked for not_proved with the first condition, or unverified. When available it is the selected route, with summary "Coordinator lost; delivery proved: pod sweep closes it by evidence, with no owner decision." Otherwise the summary is "Coordinator lost; delivery not proved (<code>): a task for the project lead." Owner handoff and successor claim remain optional routes. Prove, close, sweep and their status output contain no owner question, question field or user_direct requirement.

### R190 — Resume a parked coordinator on its Run's mail

Type: B,H,I · Scenarios: [A690](#a690), [A691](#a691), [A692](#a692), [A693](#a693), [A694](#a694), [A695](#a695), [A696](#a696)

A coordinator that owns a live worker, an unconsumed report or an awaited reply keeps exactly one outstanding supported native wait while it owns that work, and acts on what wakes it. The owner (2026-10-31) allows one outstanding blocking wait at a time, for all message types and its own work; after it returns on an event or a timeout the coordinator processes the result and arms one new wait. Busy polling, parallel waits and sleep loops stay forbidden. `pod wake --run RUN [--ack DELIVERY] [--timeout-ms N]` is the only helper: it confirms the caller is the bound coordinator of RUN, acknowledges `--ack` and returns pending mail in one native check, and only when nothing is pending arms one native wait for every message type (never a type filter). Orca keeps mail durably and ends a wait at once on a pending batch, so mail that arrives between the check and the wait's registration is returned by the wait. The helper is stateless and adds no queue, event log, daemon or scheduler.

Each result is `events`, `timeout`, `disconnected` or `fenced`. Each event keeps the native subject, body, payload, thread and priority the coordinator must process before it acknowledges, each bounded and flagged `truncated` when cut (the complete message stays readable with `orchestration check --all`, which the next action names before the acknowledgement), and is classified in native order as completion, failure, unproven completion, rejected lifecycle message (Orca delivers a rejected settlement as a `worker_done` that settled nothing, which is never a completion), decision, question, informational (heartbeat) or message; text from a worker or relay is data and never authority. A repeated message identity and a second settlement report for one Dispatch collapse to one event and are listed as duplicates, the second report with its own content. An unacknowledged batch replays with its delivery identity after compaction, a restart or a lost context and is flagged `replayed`; acknowledging a delivery Orca no longer holds reads what is pending now. A timeout is a checkpoint after which the coordinator that still owns work arms one new wait, a cancelled wait or lost connection consumes nothing and leaves no wait armed, and a fenced consumer (a rebound Run) stops without waiting. A Run the caller does not coordinate, and a wait outside its bound, are refused before any native call.

The Orca adapter passes only the exact shapes `orchestration check --run RUN [--ack D] [--wait --timeout-ms N] --json`, bounds the process by the native timeout plus a grace period and the output by the adapter limit, requires a delivery identity for every batch, and keeps the native code of a mailbox refusal. The helper keeps no state and no armed flag. `pod status` reports `wake` for a coordinator that owns work: an outstanding or unverified assignment, a settled admission whose report or disposition is still to be consumed (the finalization predicate), an authority wait, or an objective question not recorded as resolved (unknown resolution counts and is reported as unknown); `wait` is `unknown` because Orca exposes no queryable mailbox-wait state, and `quiet_with_owned_work` marks a coordinator whose terminal Orca last saw output from at least three minutes ago as a candidate for a missed wake, with the supported next action; it is never a verdict.

What the runtime can do is stated and not assumed: Orca delivers and ends a wait but cannot resume an agent, a background command's exit resumes an idle Claude Code session, and an idle Codex coordinator was observed not to resume when its background wait returned on a message, while a Codex coordinator holding a wait inside an active turn was seen processing messages. Live proof on real coordinators stays NOT_RUN until recorded.

### R200 — Retry a delivery failure once, then diagnose the receiver

Type: B · Scenarios: [A730](#a730), [A731](#a731), [A732](#a732), [A733](#a733), [A734](#a734), [A735](#a735), [A736](#a736), [A737](#a737)

A delivery failure is an attempt Orca failed at `agent_readiness` before any input was written. Pod recognizes it only from the fresh exact read of the bound Dispatch: worker `failed` at that stage, no `dispatch_input` effect, no observed start and every other effect resolved by the same classification a held claim uses (a setup still running or failed, or a closed terminal, is not resolved), the existing retry eligibility (failed Dispatch, exited agent, known resources) and no held claim. Input written, an observed or unknown start, an unrecognized stage, a stop the read does not prove, a timeout, an absent request and silence are never positive evidence of non-execution; a lost acknowledgement is recovered by its own request identity and starts nothing. Only the first attempt's delivery failure earns one automatic retry. In the same admission call, once the failed result has its ordinary `discarded` disposition (otherwise the retry is reported refused with that exact next action, and repeating the identical admission starts it), Pod re-admits the same frozen packet, plan and placement through `retry_of`, so every first-start fence, including the current candidate and packet, applies again and a changed assignment is refused with its precise code and never replayed. The retry has the deterministic identity of an explicit `retry_of`, so repeating the admission recovers that one attempt, a coordinator-chosen retry is never doubled, and a retry whose native call was interrupted is reported unresolved and recovered by its request. A retry that also fails, a receiver visibly parked on a prompt (`observation.agentWait`) or a start Orca reports as blocked (`Agent startup blocked: <token>`) returns one bounded diagnosis from native fields and the receiver's rendered screen, at once for a blocked receiver, and sends no further instruction, answers no prompt and routes around neither Orca's own circuit-breaker nor a Task/Run boundary. No counter or marker is stored; every decision reads fresh native state.

The diagnosis names the cause (`second_delivery_failure`, `startup_blocked`, `receiver_waiting`, `unrecognized_failure_stage`), both attempts, the receiver's state, stage, engagement and blocked reason, and one `screen` class from a closed vocabulary (`update_prompt`, `trust_prompt`, `login_required`, `usage_limit`, `unrecognized`, `unreadable`) obtained by one read-only `terminal read --screen` of the exact worker terminal bounded to 40 rows; the screen text is classified and discarded, never stored or shown. A same-Task retry replays Orca's original Task spec and has no replacement-prompt flag, so a retry whose assignment (candidate, scope, actions, report contract, criteria, context, dependencies, sources, served obligations, role or boundary) differs from its parent's is refused with `assignment_changed` and no start, for an automatic and an explicit `retry_of` alike (a different route or revision is not a different assignment, and a review retry deliberately re-reviews the then-current candidate). Each admission keeps one digest of its assignment in its `recovery` record for this comparison; a parent admitted before the digest existed is compared on the candidate, obligations, role, boundary and sources its row keeps; a changed assignment is admitted as its own Task after the failed attempt is settled and discarded.
