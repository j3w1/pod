# Pod v0.3.0 candidate

Pod 0.3 makes the Orca boundary explicit: Orca owns Runs, Tasks, Dispatches, request
recovery, messaging, terminals/resources and worker lifecycle. Pod stays a thin coordination
policy and evidence layer.

The new `pod-context/v2` stores admissions, checkpoints, interventions, source rejections and
legacy archive references. It no longer stores Delivery or cleanup state. Admissions bind
route, packet, grant, request and effective-launch evidence to exact native identities, while
fresh Orca projection decides current occupancy.

Lost-start recovery records Orca's UUID and follows `request-show`: completed receipts are
bound, pending requests are joined with the same UUID, and absent results permit only one
exact matching native attempt. Ambiguity holds; Pod never creates a replacement retry loop.

Existing v1 state requires the explicit private `state-migrate` operation. It creates a
verified immutable archive, resolves only exact bindings through Orca reads, conservatively
holds uncertainty and atomically installs v2. Diagnostics never migrate automatically.

This is a candidate note, not release evidence. Hosted CI, live provider/Orca checks,
independent review, project acceptance, tag, release and publication remain separate. Until
a 0.3.0 release actually exists, installation documentation stays pinned to published
`v0.1.2`.
