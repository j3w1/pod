# Pod v0.3.0 candidate

Pod 0.3 makes the Orca boundary explicit: your coding session coordinates a pod
of workers, while Orca owns Runs, Tasks, Dispatches, actual capacity, request
recovery, messaging and worker lifecycle. Pod holds the objective's routing,
logical fan-out and evidence policy.

The new `pod-context/v2` stores admissions, checkpoints, interventions, source rejections and
legacy archive references. It no longer stores Delivery or cleanup state. Admissions bind
route, packet, grant, request and effective-launch evidence to exact native identities, while
serialized objective-local reservations and exact assignment settlement decide logical fan-out.

Account routes now use Orca's redacted selected-account identity as the one approval, quota,
logical-admission and grant key. Labels cannot prove identity, account rotation invalidates the old
approval/grants, and identity plus billing proof must come from the same managed, native-default
or exact login context. The join is repeated immediately before start and pending replay, so a
rotated read is never relabeled as the approved account. All-Run and unscoped worker enumeration
are rejected by the adapter; Pod does not infer physical capacity or rebuild a shadow lifecycle.
Governor mutations join the caller's stable current Run/coordinator/generation to the objective
refs, runtime and existing Pod owner, while read-only status stays available.

Lost-start recovery records Orca's UUID and follows `request-show`: completed
receipts may bind after later policy revocation, pending requests are joined
with the same UUID only under current authority, and method-less absent results
permit only one exact matching native attempt. Contradictory request identities
remain unresolved even after a later incomplete response. A coherent,
authoritative `capacity_full` refusal becomes a durable deferral; ambiguity
never starts a replacement retry loop.

The selected model, effort and account route stay fixed for each assignment.
Pod compares requested and effective launch evidence after start. Guaranteed
noninteractive provider startup before task input still depends on a scoped
Orca launcher feature; Pod neither handles provider prompts nor changes shared
provider settings.

Existing v1 state requires the explicit private `state-migrate` operation. It creates a
verified immutable archive, resolves only exact bindings through Orca reads, conservatively
holds uncertainty and atomically installs v2 from a bounded regular file. Exact assignment
settlement closes a migrated binding regardless of terminal retention; diagnostics never migrate
automatically.

This is a candidate note, not a release announcement. See
[current progress](../pod-progress.md) for separate offline, review, hosted,
live and acceptance evidence. Until a 0.3.0 release exists, published-release
installation remains pinned to `v0.1.2`.
