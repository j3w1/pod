# Recovery

On resume read native state first, retaining uncertainty and next safe action. Continue accepted work within scope/authority; restore relevant lost guidance. After a relaunch or model switch, repeat the display readback from the worker-tab guidance and follow its next action, so tab and worktree names are re-applied.

Retained evidence uses one immutable storage format from an objective's first write. Supported preceding physical records convert on their next accepted write. For explicit lossless conversion:

1. Run `pod internal storage --input FILE` with `{"project": "<project-path>", "objective": "<objective>", "action": "inspect"}`. Inspection writes nothing and returns the exact source `revision` and `sha256`. Add `"record": "governor"` for that journal; context is the default.
2. Submit the same project, objective and record with `"action": "migrate"` and those exact `revision` and `sha256` values. Conversion validates and preserves every logical value and evidence item, publishes verified immutable chunks, and switches only that record's authority. An identical completed conversion replays without a semantic write; changed source facts require inspection again. Continued, evidence-closed records and records ended by historical retirement keep their write fences. Physical conversion does not reopen an ordinary closed objective.
3. Use `"action": "audit"` for an explicit full retained-evidence check. A missing or corrupt chunk remains unavailable evidence; preserve it and arrange recovery. Neither conversion nor an audit changes proof validity or clears native work.

Conversion needs no owner decision and calls no native/provider operation. The preceding `record-compaction` entry is read-only and directs requests here. Earlier binaries deliberately refuse the current physical discriminator; use a compatible reader and do not follow their old advice to start another objective or archive/remove the record.

Writes queue replaced roots for later physical cleanup. `pod status` and `pod doctor` show queued bytes; `"action": "gc"` explicitly runs a bounded, interruptible sweep outside the record lock. Automatic cleanup runs after migration, install/update, and at the queued-byte threshold after a writer releases its lock. A live reader, corrupt root or interrupted sweep defers cleanup without changing authority or repeating accepted work. Above the 8 MiB conversion-input bound, preserve the record and arrange supported recovery; do not remove evidence for space.

`preference_changed`/`preference_revision_stale`: on preference races, rechoose at most twice, then report the conflict. Submitted starts retain their route; recover that exact request. No added retry counter.

Failed, refused or unknown starts require Orca request/readback before replacement. Effect-free native refusals defer; uncertain effects remain unresolved. Preserve immutable response evidence and Orca's UUID; missing storage grants no authority. Follow the helper's diagnosis rather than blind replay.

For an original unobserved-start request that Orca has subsequently fenced as abandoned, repeat its identical `pod internal admission` input and add `"abandoned_reason": "<why this exact failed assignment is being accounted>"`. Keep the original objective, Run, Task, packet, plan, placement and any retry/reuse references. This explicit accounting path performs reads only and never replays worker-start. It requires the immutable positive `turn_start_unobserved` receipt and exact accepted/unobserved input effects, together with current native failed/abandoned settlement and its capability-revocation fence. Missing, conflicting or observed-start evidence stays held for native reconciliation; ordinary silence and an abandoned label alone do not qualify.

The returned `action: accounted_abandoned` binds assignment identity and settles the admission as nonsuccess without evidence. Orca's fence does not stop the process, so the logical slot frees only when the same native read reports the process exited with no pending effect (`release: process_exited`), or, for a local attempt whose reused or retained terminal Orca will not release, when Pod's own read shows that exact terminal handle and incarnation gone from Orca's complete terminal records with no same-user process carrying the handle (`release: terminal_closed`, never a success, start or report; capture `orca terminal list --json` and the `worker-show` before and after closing, and re-run the accounting); released-resource bookkeeping never overrides a live or unverifiable process, and the claim is read fresh for every bound abandoned attempt, accounted or not; otherwise the result carries a `hold` naming the worktree and branch, the slot stays outstanding and blocks readiness, and a later exit or release read frees it without repeating the accounting. A settled attempt with no live claim is history for the Governor and finalization, not a readiness veto. The hold refuses another assignment in the same worktree or branch (`abandoned_claim_held`) and any overlapping paths or surfaces, counts for every Governor unit, and clears only on positive exit with no pending effect. Orca's harmless observations are never pending: the worktree, the accepted input, a setup that was not applicable, skipped or completed, and a created or reused terminal. A pending `push` blocks that ref in its own repository only; any other pending effect, or one without an identity, blocks other worktrees in every repository until Orca reports it resolved. An independent worktree and branch stays usable. A current readback that shows an observed start is accounted the same way with execution `observed`, whether the admission was unresolved or already bound. A reviewer or implementer that produced no output completes without a manufactured report (an implementation still takes the discard below); investigation is a tracked follow-up. Its `abandoned_accounting` record preserves execution as UNKNOWN, the actual accounting coordinator/reason, original error, raw observations and fence; an unavailable native abandoner or abandonment reason stays UNKNOWN. It does not prove the input never executed, process exit, release, accepted output or delivery. Do not submit a worker report or integrate output through this path. For an implementation, record the existing ordinary checkpoint disposition `{"admission": "<original-admission-id>", "discarded": true, "reason": "<why no accepted output is used; preserve unknown execution/resources>"}` with the next map sequence before replacement work. Keep possibly-live or user-requested retained resources and all current Governor/source/policy guards. This accounted attempt cannot be a reuse or retry parent. Repeating the same accounting is idempotent; it creates no Task or Dispatch, and a different reason cannot overwrite the record. Once written, the explicit admission field requires a reader that supports this accounting; preceding readers refuse it without rewriting.

A new same-Task retry requires the owned parent's exact failed/stopped outcome and terminal Dispatch status, a positively `exited` agent and known resource disposition. Silence, stale status, proposed or failed stop, `unverifiable` liveness and pending/unknown release remain held. Assignment settlement alone does not prove process exit. Orca owns stop, release, retry failure counters and its circuit-breaker; complete any uncertain native action through its returned recovery command. A failed Dispatch does not prove that its Task is startable. Keep a native `task_not_startable` and its returned next action; the coordinator handles any Task-status/cancellation prerequisite through Orca, outside Pod's mutation adapter. A circuit-broken `task_not_startable` remains refused: report it without escaping through a new Task or Run. Safety and permission holds still apply; an active recorded `auth_failed` also holds same-Task retries across routes until its existing clear/expiry conditions are met. Record the actual failure through the existing route-failure contract rather than inventing a provider parser or health cache.

A first attempt Orca failed at `agent_readiness` with no input written, an exited agent, known resources and no held claim is a delivery failure. After its ordinary `discarded` disposition, the same admission call (or the identical repeat) starts exactly one retry of the same frozen packet through `retry_of`; before the disposition the helper reports the retry refused with that next action. The retry's result is `delivery.action: retried`. A lost acknowledgement, a timeout, an absent request, written input, an observed or unknown start, an unrecognized stage and an unproved stop are never proof of non-execution and start nothing: recover by the request or exact readback. A receiver parked on a prompt (`observation.agentWait`) or a start reported as `Agent startup blocked: <token>` returns `delivery.action: diagnosis` at once; so does a retry that also fails. Read its `cause`, `attempts`, `receiver` (including `screen`, one class from a single bounded read-only `terminal read --screen`: `update_prompt`, `trust_prompt`, `login_required`, `usage_limit`, `unrecognized` or `unreadable`; no screen text is kept) and `next_action`. Pod then sends no instruction, answers no permission, authentication, security, spending or preference prompt and starts no third attempt; the person or policy who owns the prompt resolves it in the receiving session, then admit again with the same `retry_of`. A changed candidate, plan or packet is refused with its precise code, and an assignment (served obligations, role, boundary or sources) that differs from the retry parent's is refused as `assignment_changed`, never replayed as the same operation; admit it as its own Task after the failed attempt is settled and discarded. `retry_unresolved` means the retry may have started: repeat the identical admission to recover it by its request.

An explicit fresh intent is supported only after a proven recoverable no-start: an authoritative `task_not_startable` bound to the exact Run, Task and retry parent, typed `status: blocked` or `status: ready` and no nonempty `reason`, or the helper's durable caught pre-start parent-read/eligibility failure. Native refusal IDs are optional: immutable start-invocation provenance can supply omitted Run/Task/parent IDs; any present contradiction holds. Without that provenance or complete exact IDs, or without either supported typed status, fresh intent stays held. Inspect the evidence and correct the prerequisite first, then use the fresh-intent syntax in the admission guidance. A READY Task cannot retry: its genuine coordinator must resolve the native status prerequisite through Orca under existing authority; the original READY refusal stays unchanged. Native retry still requires a currently failed or blocked Task and validates its policy; Pod never updates Task state. `status: failed` in the original refusal (including circuit break), another refusal reason or an unrecognized read failure stays held.

The helper's pre-start sidecar records its own control flow before any start invocation, not native proof. Its immutable recovery reference preserves the evidence when authority/contact is lost; recording it cannot defer or free the reservation. Deferral requires the normal current native authority join at that invocation's runtime. After contact and authority return, repeat the identical admission or recover its exact admission: the helper can classify the persisted exact admission/Run/Task/parent evidence without starting. Then use an explicit fresh intent after correcting the prerequisite. An older invocation cannot classify a row rebound to another runtime. Missing/corrupt evidence and a crash gap cannot establish no-start, even with no UUID or start observations. They retain the original reservation and exact attempt recovery. A proven runtime rebind uses existing recorded continuity to validate the original evidence's observed runtime without rewriting its bytes; missing lineage holds.

A real permission prompt or permission stop remains blocked at the coordinator's policy boundary until its authorized resolution. Never classify it as availability or safety to obtain a different route, and never reroute it. Pod does not infer permission-stop causes from provider prose or add a new failure category; a native permission refusal stays unresolved. Existing safety and authentication records retain their own holds.

Repeat the identical retry admission input to recover its one immutable attempt, including an earlier deferred refusal. A changed packet, plan or placement cannot replace that retry. Completed request recovery records its receipt; pending recovery joins only the original UUID with its admitted route and exact `--retry-of`; absent or missing-UUID recovery inspects the same Run/Task and requires one child with exact native `retryOfDispatchId`. Earlier owned attempts, including the original parent, cannot become the new child. After start, binding/adoption verifies the immutable parent link and current authority; a parent's subsequent release transition does not invalidate its child. The actual child worktree is resolved by its exact native id and must join the admitted Git repository, path and branch. Different or unreadable placement holds without a new start; a known own-child placement contradiction also stays held across later incomplete reads. Missing or ambiguous evidence holds without a fresh start. A known own-receipt/child wrong-parent contradiction stays held even if a later read omits the field; an unrelated inventory row instead leaves recoverable ambiguity. Report the helper's next action and retain the original raw evidence.

Terminal reuse requires settled prior attempt and known terminal, copies its effective route, and rechecks eligibility/pin; native `worker-start --terminal` has no model/effort flag.

Keep raw failure source, stage and time. Readiness timeout leaves cause unknown. Honor native retry-after; otherwise temporary unavailability gets 60-second local reconsideration. Expiry neither starts work nor proves recovery. Validated success clears suppression while retaining history. Past failures impose no permanent/family ban; auth/rate limits need expiry or meaningful runtime/user change. Preserve unavailable pins; no probes, shared health cache, rotation or blind retry. Actual failures require settlement/no-start before another route.

`installed_version_changed` requires skill reload, fresh config read and authorized Pod-stamped checkpoint before new admission/Governor mutation; recovery is exempt.

For a recognized Codex software-update menu, require live native `terminal read --screen` readback with `source=screen` and displayed **Skip for now** option/control. Through supported `terminal send`, send only its displayed selector (shown number/key; Enter only if shown) once, verify readiness, then resume normal admission/recovery at the same model/effort. Unproven controls block; never guess input. Ambiguous transport requires exact native `--retry-request` recovery, never resend. No installation, other prompt automation, provider/settings/permission/safety changes, duplicate pending requests or retry/controller loop. Missing live opt-out proof stays NOT_RUN.

For a lost coordinator, read `pod status --objective ID --json`. Its `evidence_closure` recovery route names whether delivery is proved and any conditions still unmet. Run `pod sweep --objective ID --json` in the repository to close proved delivery without an owner decision. The sweep proves coordinator loss, settled native work, the source's ticked PoDs or completed issue (for a claim-only successor, the issue its claimed chain binds), and every recorded delivery PR merged on GitHub. With none recorded, exact-target merged PRs linked by GitHub to each bound source can prove delivery; unavailable retained target identity stays unavailable and no Governor delivery record is invented. It preserves unavailable results as UNKNOWN, never stamps them, and keeps original record bytes, including older supported records. It needs no terminal or Run binding and changes no Orca or Git state. Its acknowledgement separately reports the bound-source completion effect and any lead tasks; sweep also retries this effect for ordinary closures.

After an owner-authorized Orca stop or restart window, a coordinator the window ended continues without an owner decision. Open a new terminal in the objective's recorded worktree and read `pod status --objective ID --json`. When its `window_continuation` block is available, run `pod continue --objective ID --json` there. The host's authorization verifier proves the window, and Pod proves the loss, the unchanged place, the Run and each admission's identity. The command rebinds the existing Run through `run-use` and records derived provenance; it never records an owner decision. Settled, unknown and absent admissions are only recorded, so recover them afterwards through the ordinary paths. Rerunning the same command finishes an interrupted continuation, and a second terminal is refused. `pod status --list` shows each open objective's continuation step, or the condition that blocks it, as a task for the project lead. A repository move or a changed worktree cannot be continued. Owner handoff and successor claims stay available with their own decisions.

If delivery is not proved, keep the objective open as a task for the project lead, never an owner question. A live coordinator records its own closure. For unfinished work, owner handoff and successor claim remain optional authority paths with their existing decisions. Continuing by claim uses `internal succession` after the successor's first checkpoint, before work, with a `user_direct` decision on its facts; a claim is unnecessary for proved delivery.

Governor failures use `governor-classify`: code defect returns to correction, remote-only names bounded discriminating check/stop, transient follows bounded policy retry, external names dependency; unclassified failures defer.

Historical retirement is optional abandonment, never confirmation of delivered history. Detection retains every missing completion condition as a lead task, including mixed requests. Prefer resolving those conditions and sweeping proved delivery; only an explicit authority decision to abandon a record uses R112's existing exact-facts decision path.

Decision-policy or tool-permission drift requires a current check and fresh applicable decision; it cannot be repaired by replaying a stale worker summary. Readers predating decision-channel marker 5 refuse new decision records without rewriting them. Once new decision evidence has written that marker, use Pod 0.21.18 or newer; ordinary lossless maintenance alone does not impose that floor on older records, and never removes an existing marker. Older config readers also refuse the new personal decision fields. Preserve those records and use a compatible reader rather than deleting authority history for rollback.
