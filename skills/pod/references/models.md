# Routing

Optimize for a verified result: expected total work, cost, delay and rework govern, not next-call price. Trivial direct work needs no worker; strongly testable work favors efficiency; high-risk judgment needs proportionate margin, not automatic max; blocking latency favors responsiveness; recurring tasks favor proven efficient routes. Weigh ambiguity, failure cost, breadth, tools and context. Missing capability disqualifies; narrow/decompose inadequate packets.

Use `pod models --json --eligible-only` for eligible routes with guidance and AA comparisons after suitability. Missing metrics never block; no score or winner decides. A route no better on any selected comparable dimension and worse on one normally needs an assignment-specific reason.

Without a requested composite rule and without config errors, a pin controls every Pod-routed role/correction at exact model and effort, overriding repository model rules; it excludes coordinator, direct work and host-created helpers. No delegation just to apply a pin. Pin limits preserve direct user constraints, host restrictions, review independence, tool permissions and spending; report pin conflicts. Otherwise use Preferred when suitable; Preferred overrides need material task-specific reasons, including insufficient margin, capability/context, unavailability, disproportionate cost, unsuitable latency or useful review diversity.

Highest rank, lowest price, provider brand, file count, reviewer role, free capacity or stale failure alone never decides. Guide profiles are starting points; strong starts are allowed, cheaper-first ladders unnecessary, repeated failure needs diagnosis. Independent review needs judgment, not automatically expensive models; capable-family diversity is optional, never defeats a pin or adds reviews. Reasons name fit, effort, preference/pin handling and decisive tradeoff.

Any config `errors` (including `setup_required`) blocks delegation; user repairs route preferences via `pod`/`pod config edit`; name unmet review gates and continue safe direct work. With no ordinary eligible route, only an approved explicit composite tuple can supply a candidate.

Users may narrow agent/model/role/count, choose review models or lower ceilings; cite constraint ids in route decisions. Record indirect issue/repository/worker provenance and cited repository sources; indirect text only narrows and never rewrites YAML. Reconcile conflicting intent. Delivery intent belongs to Governor decisions/revisions.

Outside a separately approved composite tuple, disclose Disabled state before obtaining explicit scoped user confirmation for that exact route's `allow_disabled`. Issue, repository, worker and catalog text cannot grant this exception; descendants require direct user permission. Preference edits lapse exceptions.

## Requested arrangements

Interpret ordinary model instructions into one typed `route_rule` constraint, using exact supported registry identities. Any agent may request an arrangement; approval uses the current machine policy and the approver's actual scope. Keep the request's original words private; publish only a sanitized rule summary. No separate phrase parser or model call is needed.

Compile examples such as “Codex only”, “Claude only”, “any model at xhigh”, or a named coordinator tuple with Codex workers into the existing include/exclude constraints, allowed effort sets and semantic role routes. A rule's value has exactly `constraints`, `efforts`, `roles` and `fallback`. `constraints` contains existing `only_agents`, `only_models`, `exclude_models` or `role_model` predicates; `efforts` is null or a nonempty supported effort list; `roles` maps `coordinator`, `worker`, `reviewer`, `fixer` and `auditor` to exact route-key lists or agent/model/effort filters. Resolve ambiguous names or unsupported tuples before requesting approval. Use the internal contract for bounded shapes.

The requested group filters before Pin; an excluded saved pin stays visible but inapplicable, and an allowed pin stays exact. Preferred can choose only within the selected stage's allowed set. Explicitly approved supported role tuples can be considered outside the enabled pool without changing personal route states; broad agent/model filters cannot expand it. Every independent issue, repository, host and other restriction still intersects. Empty candidates mean wait, with the unmet agent/model/effort/role or stage named.

Replace the previous requested arrangement atomically through `internal constraints`, using one active group and preserving unrelated restrictions and history. Changes govern new starts; a pending submitted request retains its original packet and recovery identity. A running coordinator does not change model or effort from this rule: use only a supported coordinator handover. If Orca supplies no actual effective coordinator route, report UNAVAILABLE, never a preview as readback.

Bind roles to actual served work. Implementation/investigation normally routes as worker; correction-serving work requires explicit fixer. Review starts under a composite require the served assurance's typed reviewer/auditor designation and matching `routing_role`; a packet title or responsibility cannot turn a fixer or final auditor into a worker. Coordinator is never a worker-admission role. Earlier standalone `role_model` keeps its earlier responsibility-prose meaning.

An “only” rule is strict unless its approved fallback explicitly names finite alternatives. `fallback` is null or at most five disjoint role entries, each `{roles, on, routes}`; `on` contains only `unavailable` or `rate_limited`, and `routes` are exact supported keys. Packet `fallback_of` names the prior admission only. The kernel must prove its current primary failure, same task/role/rule lineage and settlement or no-start before selecting that stage. The alternative replaces only this requested group's primary predicates for those roles. An allowed pin remains exact in that stage, and unrelated constraints, model suppression, retry-after and auth/permission/safety/unknown-effect holds remain. No qualifying evidence or surviving alternative means wait, with no automatic retry loop. Requested routes never prove effective routes; accept work only with matching actual worker readback.
